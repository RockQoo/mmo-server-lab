# 001. 서버 구조: 분산 존 (Gateway + Zone)

날짜: 2026-11-23 · 종류: 설계 선택 (벤치마크는 구현하면서 단계별로 붙인다)

## 질문

MMORPG 서버를 어떻게 나눌까? 데이터의 주인은 누구이고, 패킷은 어디를 거치며, 존 이동과 서버 간 전쟁은 어떻게 처리할까?

## 후보

진짜 데이터가 서버 메모리에 있고 DB에는 나중에 모아서 저장하는 "메모리 기준" 구조 다섯 가지를 비교했다.

| 구조 | 데이터 주인 | 패킷 경로 | 얻는 것 | 잃는 것 |
|---|---|---|---|---|
| **A. 분산 존** | 플레이어가 있는 Zone | 클라 → Gateway → Zone | 주인이 한 곳, 중계 한 번, 존·서버를 따로 늘림 | Zone이 죽으면 마지막 저장 이후 손실, 존 이동 중 패킷 처리, 서버 종류가 많음 |
| B. 채널 | Game 서버 (프로세스 하나 = 채널 하나) | 클라 → Game | 가장 단순, 디버깅 쉬움 | 프로세스 하나에 동접 상한, 채널을 넘는 기능은 별도 처리 |
| C. 홈 서버 | 상위 서버(홈)가 캐시 | 클라 → 중계 → 홈 → Zone | Zone이 죽어도 데이터가 살아남음 | 홈과 Zone이 데이터를 나눠 들어 맞추는 코드, 중계가 한 번 더 |
| D. 액터 | Player 액터 | 클라 → Gateway → 액터 | 콘텐츠 코드가 짧고 런타임이 배치 | 50ms 틱, AOI 브로드캐스트 같은 실시간 전투와 맞지 않음 |
| E. 공간 분할 | 서 있는 셀 | 클라 → Gateway → 셀 | 로딩 없는 넓은 월드 | 경계 너머 전투, 사본 동기화. 난이도 매우 높음 |

## 결론

**A. 분산 존**으로 간다.

- 데이터 주인이 한 곳이라 맞춰야 할 사본이 없다.
- 이동·전투 패킷이 Gateway 한 번만 거쳐 Zone에 간다.
- **존 이동(handoff) 코드 하나가 나중에 서버 간 전쟁 코드가 된다.** 원래 Zone이 플레이어 데이터를 직렬화해 전장 Zone에 넘기는 것이 평소 존 이동과 같다.
- 측정할 거리가 많다: Gateway 세션별 묶음 전송(send 호출 수), 존 틱 지연, handoff 지연, Gateway 경유와 직접 접속 비교.

B로 먼저 만들고 나중에 나누는 길도 있지만, 그러면 나누는 작업을 한 번 더 한다. 처음부터 실제 프로세스로 나누고 서버 종류를 단계별로 늘린다.

## 단계

| 단계 | 서버 | 대신하는 것 |
|---|---|---|
| 1 | Gateway ×1 + Zone ×1 + BotServer | Coordinator는 설정 파일, Login은 토큰 없이 접속 |
| 2 | Zone ×2, handoff(존 이동) | 이동 중 도착한 패킷을 모아 두는 처리가 핵심 |
| 3 | Coordinator (등록·배치·조회) | 설정 파일 대체 |
| 4 | DbWriter + 데이터별 저장 기준표 | Zone이 죽으면 잃는 약점을 여기서 메움. 거래·재화는 즉시 트랜잭션 |
| 5 | ServiceServer (길드·파티) | |
| 6 | 서버 간 전쟁: 재접속 방식 → Gateway 경로 변경 | 보상은 이벤트 ID(원장)로 중복 지급 차단 |

C++과 C# 서버가 같은 구조, 같은 프로토콜을 쓴다. 그래서 UE5 클라이언트와 C++ 봇이 두 서버에 다 붙는다.

## Trade-off

- **얻은 것**: 지연이 적고, 늘리기 쉽고, 존 이동과 서버 간 전쟁이 같은 코드다.
- **잃은 것**: 서버 종류가 많아 운영 부담이 크다. Zone 장애 때 마지막 저장 이후 손실(4단계 저장 기준표로 줄인다). 존 이동 중 패킷 처리가 까다롭다.
- **결론이 깨지는 조건**
  - 데이터 안정성이 지연보다 훨씬 중요해지면 C(홈 서버)가 낫다.
  - 한 맵에 수천 명이 모이는 공성이 핵심이면 그 전장만 E(공간 분할)가 필요하다.
  - 동접이 프로세스 하나로 충분하고 빨리 내야 하면 B(채널)가 낫다.
