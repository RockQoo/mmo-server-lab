# 002. 메시지 큐에 객체를 넣을까, 직렬화한 바이트를 넣을까

- 날짜: 2026-11-27
- 측정 코드: `server-cpp/Bench/MessageQueueBench.cpp`, `server-cs/Bench/MessageQueueBench.cs`

## 질문

같은 프로세스 안에서 스레드끼리 메시지를 넘길 때(예: 네트워크 스레드 → 존 Lane), 큐에 무엇을 넣을까.

- **A. 객체**: 메시지 객체를 그대로 넘긴다(C++ `unique_ptr`/ObjectPool 핸들을 move, C# 참조).
- **B. 바이트**: `ByteWriter`로 직렬화한 버퍼를 넘기고, 받는 쪽이 `ByteReader`로 다시 객체를 만든다.

B의 장점은 공유가 전혀 없어 안전하고, 같은 코드로 프로세스 밖(패킷, 서버 사이, 존 이동)에도 보낼 수 있다는 것이다. A는 복사가 적다.

## 가설

A가 빠르고, 메시지가 클수록 차이가 커진다. A는 크기와 상관없이 포인터 하나를 넘기고, B는 "객체 → 바이트 → 객체"로 최소 두 번 복사한다.

## 조건

- CPU: Ryzen 7 9800X3D(물리 8코어, 논리 16). Windows 11. C++ MSVC 19.51 Release, C# .NET 10.0.12(Workstation GC, 기본값).
- 모양: 생산자 N개(`ThreadTeam` 전용 스레드) → 소비자 M개. 메시지마다 키(플레이어 ID처럼 계속 바뀌는 값)로 소비자를 고른다(`LaneGroup::IndexFor`, 두 언어 같은 계산). 조합 1:1, 4:1, 2:2, 4:2, 4:4, 8:4(8:4는 12스레드로 코어가 모자란 경우).
- 흐름 제어: (생산자, 소비자) 쌍마다 처리 안 된 메시지가 1024개를 넘으면 생산자가 기다린다. 쌍마다 카운터를 따로 둬서 카운터를 쓰는 스레드가 늘 하나다(측정 틀이 경합을 만들지 않게).
- 메시지 2^20개. 소비자는 모든 필드를 읽어 합친다.
- 메시지 세 가지(직렬화 크기): Move 24B(값만), Chat 106B(문자열 96자), Inventory 970B(칸 60개 리스트).
- 큐
  - C++: 우리 `Messaging::Lane`(mutex + 두 vector 교체, `std::move_only_function`), M개는 `LaneGroup`.
  - C#: BCL `Channel<T>`(SingleReader, 스레드 풀 async 루프)와 우리 `Messaging.Lane`(`Channel<Action>` 위).
- 보내는 방식
  - C++: `New`(make_unique 복사), `Pool`(ObjectPool에서 빌려 복사 대입, Lane 스레드에서 반납), `Bytes`(ByteWriter → BufferPool 버퍼에 복사 → ByteReader로 새 객체).
  - C#: `New`(새 객체, string은 불변이라 참조만 복사), `Bytes`(ByteWriter → ArrayBufferWriter → ArrayPool 배열에 복사 → ByteReader로 새 객체). `DefaultObjectPool`은 `new`보다 느려서 뺐다(`docs/journal/objectpool.html`).
- 값: 메시지 하나의 시간 = 전체 걸린 시간 / 메시지 수(모든 스레드를 합친 처리량의 역수). C++은 3회 중앙값, C#은 BenchmarkDotNet 평균(반복 5회).

## 결론

1. **같은 프로세스 안은 객체로 넘긴다(가설대로).** 두 언어 모두 큰 메시지에서 바이트가 3~13배 느리다. 작은 메시지에서는 큐 비용에 묻혀 차이가 작다. 직렬화는 프로세스 밖으로 나갈 때(패킷, 서버 사이, 존 이동)만 쓴다. C++은 객체를 ObjectPool로 만든다(`new`보다 1.1~2.5배 빠르다. 스레드를 건너가는 `new`/`delete`는 할당기 경합이 크다).
2. **C++ `Lane` 큐가 N:M에서 병목이다.** Lane이 늘수록 느려진다(큐만 1:1 34ns → 4:4 69ns). 생산자가 4:4에서 한 번도 기다리지 않았는데 모든 스레드가 user CPU를 가득 썼다(메시지당 user 약 490ns, kernel 38ns): 깨우기(kernel)보다 잠금 경합과 캐시 줄 왕복 쪽이다. C# `Channel`은 생산자 4개에서 소비자가 늘수록 빨라져(4:1 104 → 4:2 71 → 4:4 47ns, C++은 47 → 87 → 69ns) N:M에서 C++을 앞선다.
   - **바로잡음(2026-11-27)**: 처음에는 "C# `Channel`은 lock-free라서"라고 적었다. .NET 소스(`SingleConsumerUnboundedChannel.cs`)를 확인하니 `SingleReader = true` 채널도 **쓰기(`TryWrite`)마다 `lock`을 잡고** 잠금 안에서 `SingleProducerSingleConsumerQueue<T>`에 넣는다. 잠금이 없는 것은 읽기 빠른 길뿐이다. 두 언어 모두 넣을 때마다 잠금을 잡으므로 차이는 잠금 안에서 하는 일에 있다.
   - 가설(Lane 개선 단위 첫 단계에서 하나씩 확인): ① `Post`가 잠금 안에서 `_thread.get_stop_token()`을 불러 stop 상태 공유 참조 카운트를 원자적으로 올리고 내린다 ② 일 하나가 `std::move_only_function` 64B(C#은 `Envelope` 24B) ③ Lane이 swap할 때 생산자와 같은 mutex를 잡는다(C#은 읽기에 잠금 없음) ④ `std::mutex` + `condition_variable_any` vs `Monitor`.
   - 언어가 아니라 지금 Lane 구현의 문제다.
3. **C++ Lane의 목표선**: 4:4·8:4에서 C# `Channel` 수준(메시지당 약 45ns, 초당 약 22M) 이상, 1:1은 지금(34ns) 이하. Lane 큐 개선 단위의 합격선으로 쓴다.
4. **직렬화가 필드마다 4~5ns다**(두 언어 모두 Inventory 쓰기·읽기 각 약 1µs). C++은 `WriteBytes`/`ReadBytes`가 .cpp에 있어 필드마다 함수 호출 + `vector::insert`다. 결론 1은 바뀌지 않지만(잘 만든 직렬화도 복사가 두 번) 패킷 경로에는 그대로 쓰이므로 Network 전에 줄인다.

## Trade-off

- 얻은 것: 같은 프로세스 안 메시지는 복사 한 번(+ 풀), 크기와 상관없이 큐에 포인터 하나.
- 잃은 것: 넘긴 객체를 보낸 쪽이 계속 만지면 데이터 경쟁이다. C++은 `unique_ptr`/`PooledPtr` move로 소유권을 넘겨 막는다(넘긴 뒤 보낸 쪽 핸들은 빈 값). C#은 언어로 막을 수 없어 "넘긴 객체는 만지지 않는다"를 규칙으로 지킨다. 같은 메시지를 프로세스 밖으로 보내는 코드는 따로 직렬화를 거친다.
- 결론이 깨지는 조건
  - 메시지를 여러 곳에 보낸다(방송): 객체는 참조 카운트나 복사가 필요하고, 바이트는 한 번 직렬화해 여러 번 보낸다. 방송은 Network 단위에서 따로 잰다.
  - C# GC 비용: 이 측정은 메시지가 곧 죽어 Gen0만 돈다. 실제 서버는 오래 사는 객체가 많아 Gen2가 커지고, `new` 방식의 할당(메시지당 32~1080B)이 틱 멈춤(p99·최댓값)으로 돌아온다. 봇 부하 테스트에서 틱 지연 p99·최댓값, `GC.GetTotalPauseDuration()`, 메모리, Server GC를 C++과 같이 잰다. 평균 처리량만으로 "C#이 빠르다/느리다"를 결론 내지 않는다.

## 측정 한계

- 큐를 거친 값(결과 1~3)에는 소비자를 깨우는 비용이 섞인다. 소비자가 빨리 끝내 큐가 비면 넣을 때마다 깨워야 해서, 일이 더 많은 메시지가 더 빠르게 나오기도 한다(C++ Chat Pool 1:1이 Move Pool보다 빠름, C++ Chat Bytes가 N:M에서 Pool보다 빠름). 순위는 같은 조합 안에서만 보고, 메시지 하나의 CPU 비용은 "큐 없이" 값으로 본다.
- C# Chat은 문자열을 복사하지 않고 C++은 복사한다(언어다운 방식을 그대로 둠).
- 첫 C# 측정은 `Channel` 경로에도 메시지마다 캡처 객체(48B)가 할당되고 있었다. 반복 안에서 envelope를 캡처하는 람다가 있으면, 컴파일러가 분기와 상관없이 반복마다 캡처 객체를 만든다(Codex 리뷰 R1). 람다를 함수로 빼서 다시 쟀다. 위 C# 표는 고친 뒤의 값이다(큐만 1:1 65 → 50ns. N:M 값은 거의 같다).
- 측정 틀의 Noop도 물리 8코어 8스레드에서 약 5배까지만 는다(`docs/journal/objectpool.html`). 조합 사이의 확장 배수는 결론으로 쓰지 않는다.
