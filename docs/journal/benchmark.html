개발일지 · 벤치마크

측정 방법 · 2026-11-26 · 첫 벤치마크(BufferPool)에서 측정 도구가 결과를 왜곡한 일. 벤치마크를 만들 때마다 여기 확인 목록을 본다

한 줄 요약. C++ 여러 스레드 측정이 모두 실제보다 크게 낮게 나왔다. 풀 코드가 아니라 측정 코드가 원인이었다. 매 반복 부른 benchmark::DoNotOptimize()가 MSVC에서 전역 변수 하나에 값을 써서, 모든 스레드가 같은 캐시 라인을 두고 다퉜다(true sharing). 스레드마다 자기 변수에 쓰게 바꾸자 정상으로 돌아왔다.

언제부터

이 프로젝트의 첫 벤치마크다. 2026-11-26 Google Benchmark(C++)와 BenchmarkDotNet(C#)을 설치하고(2209890), BufferPool 1판과 new/delete, C# ArrayPool을 처음 쟀다. 그 전까지 server-cpp/Bench/는 빈 폴더였다.

무엇이 이상했나

아무 일도 하지 않는 반복(Noop)을 스레드 1개와 8개로 돌렸다. 코어 8개가 동시에 일하면 8배 가까이 나와야 한다.

스레드 1개스레드 8개배수
기대약 600M/s약 4,800M/s8배
C++ Bench 실제627M/s735M/s1.2배

할 일이 없는 반복조차 늘지 않는다는 것은, 스레드를 8개 띄워도 실제로는 1~2개만큼만 일한 것과 같다는 뜻이다. 이 상태에서는 "풀이 스레드가 많을 때 경합하나"를 볼 수 없다. 모든 방식이 똑같이 눌리기 때문이다.

원인: DoNotOptimize가 전역 변수에 쓴다

DoNotOptimize(x)는 "x를 누군가 쓴다"고 컴파일러를 속여 계산이 지워지지 않게 하는 장치다. GCC·Clang용 구현은 인라인 어셈블리라 메모리에 아무것도 쓰지 않는다. MSVC는 인라인 어셈블리가 없어서, x의 주소를 라이브러리 안의 전역 volatile 변수 하나에 저장하는 방식으로 구현되어 있다.

확인(vcpkg Google Benchmark 1.9.5): benchmark.h의 MSVC 분기는 internal::UseCharPointer(&x)를 부르고, benchmark.dll을 역어셈블하면(dumpbin /disasm) 그 함수는 받은 주소를 고정 주소 하나에 저장하고 끝난다.

?UseCharPointer@internal@benchmark@@YAXPEDD@Z:
  mov  qword ptr [180047C08h], rcx   ; 인자(주소)를 전역 변수 하나에 저장
  ret
  • 스레드 하나일 때는 문제가 없다(혼자 쓰니 줄이 그 코어에 계속 있다). 그래서 스레드 1개 결과는 맞았다.
  • 스레드가 여럿이면 매 반복 그 줄이 코어 사이를 오간다(캐시 라인 핑퐁, 한 번에 수십~100ns). 몇 ns짜리 일을 재는데 매번 수십 ns가 더해지니, 스레드를 늘려도 처리량이 늘지 않았다.
  • 1판 BufferPool이 느렸던 이유(모든 스레드가 같은 mutex·카운터에 씀)와 같은 현상이 측정 도구 안에서 일어났다.

용어: true sharing과 false sharing

이름상황고치는 법이 프로젝트의 예
true sharing(진짜 공유)여러 스레드가 같은 변수를 실제로 함께 씀공유를 없앤다(스레드마다 자기 변수)이번 DoNotOptimize의 전역 변수, 1판의 _rented 카운터·mutex
false sharing(거짓 공유)스레드마다 다른 변수를 쓰는데, 그 변수들이 같은 64바이트 캐시 라인에 붙어 있음캐시 라인 단위로 떨어뜨린다(alignas(64), 패딩)RuidGenerator의 원자 변수를 alignas(C++)·128바이트 패딩(C#)으로 따로 둔 것

둘 다 결과로 나타나는 현상은 캐시 라인 핑퐁(캐시 라인 경합)이다.

고친 것

// 전: 모든 스레드가 라이브러리 안 전역 변수 하나에 쓴다
for (...) { auto buffer = Rent(size); benchmark::DoNotOptimize(buffer.Data()); }

// 후: 스레드마다 자기 스택의 volatile 변수에 쓴다(다른 스레드와 겹치지 않음)
std::byte* volatile sink{};
for (...) { auto buffer = Rent(size); sink = buffer.Data(); }

커밋 4e8eaee. 바로잡은 수치는 bufferpool.html의 "바로잡은 측정".

벤치마크를 만들 때 확인 목록

  1. Noop 기준을 같이 잰다. 같은 측정 틀로 아무 일도 하지 않는 반복을 스레드 1·2·4·8개로 돌린다. 스레드 수만큼 늘지 않으면 측정 틀에 공유 자원이 있다. 그 상태의 여러 스레드 결과는 믿지 않는다.
  2. 여러 스레드 반복 안에서 benchmark::DoNotOptimize를 쓰지 않는다(MSVC). 스레드마다 자기 volatile 변수에 쓴다. 스레드 하나짜리 측정에서는 써도 된다.
  3. 측정 코드 안의 공유 변수를 찾는다. 정적·전역 변수, 같은 배열의 이웃 칸(false sharing), 모든 스레드가 매 반복 쓰는 카운터.
  4. 다른 방법으로 한 번 더 잰다. 이상하면 표준 C++만으로 작은 프로그램을 만들어 같은 일을 재 보고, C#과 같은 일(Noop)도 비교한다.
  5. 스레드 1개 값부터 본다. 공유 문제의 영향을 받지 않아 가장 믿을 만하다. 여러 스레드 값은 1번을 통과한 뒤에 본다.
