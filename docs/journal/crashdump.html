개발일지 · 덤프 분석

CrashDump · 2026-11-27 · 남긴 덤프를 WinDbg로 실제로 열어 콜스택이 보이는지 확인한 일, release 심볼이 없던 문제, 데드락 찾는 법. 서버가 죽거나 멈췄을 때 여기부터 본다

한 줄 요약. CrashDump 테스트는 "파일이 생겼고 비어 있지 않다"까지만 봤다. WinDbg로 직접 열어 보니 C++·C# 덤프 모두 크래시 위치와 모든 스레드 스택이 보였다. 다만 release 빌드는 심볼(.pdb)을 만들지 않아 실제 서버 덤프는 주소만 남을 뻔했다. release에도 pdb를 만들게 고쳤다(db47532).

왜 열어 봤나

덤프는 "남았다"보다 "열어서 원인이 보인다"가 목적이다. 파일 크기만 보는 테스트로는 다음을 알 수 없다.

  • 크래시 덤프에 넣은 예외 정보(RtlCaptureContext로 직접 만든 것 포함)가 디버거에서 원래 스레드 스택으로 이어지는가
  • 스냅샷(PssCaptureSnapshot) 덤프는 복사본 프로세스를 쓴다. 스레드 목록·레지스터가 빠지지 않는가
  • 나중에 서버가 멈췄을 때(데드락) 수동 덤프로 원인을 찾을 수 있는가

도구 준비

WinDbg(MS 공식 디버거). 설치하면 명령줄 디버거 cdb.exe가 같이 들어온다. 라이브러리가 아니라 도구라 저장소에는 아무것도 추가되지 않는다.

winget install Microsoft.WinDbg

# cdb 위치(스토어 앱이라 PATH 에 없다)
$cdb = (Get-AppxPackage Microsoft.WinDbg).InstallLocation + "\amd64\cdb.exe"

GUI로 보려면 WinDbg를 열고 File → Open dump file. 아래 명령은 GUI 아래쪽 명령 창에 그대로 쳐도 된다.

심볼(.pdb)

덤프에는 메모리와 주소만 있다. 주소를 함수 이름·줄 번호로 바꾸는 것이 pdb다. 덤프를 남긴 exe와 같은 빌드의 pdb가 있어야 한다.

무엇어디서
우리 코드exe 옆의 *.pdb (server-cpp/build/<config>/). 배포할 때는 빌드마다 exe와 pdb를 같이 보관한다
Windows·CRT DLLMS 심볼 서버: srv*<캐시 폴더>*https://msdl.microsoft.com/download/symbols
vcpkg DLL(gtest 등)build/<config>/vcpkg_installed/x64-windows/(debug/)bin. 빠뜨리면 그 프레임만 엉뚱한 함수 이름으로 나온다(우리 코드 프레임은 맞다)
& $cdb -z <덤프.dmp> -y "<exe 폴더>;srv*C:\symcache*https://msdl.microsoft.com/download/symbols" -i "<exe 폴더>"

바로잡음: release 빌드에 pdb가 없었다

전

release 프리셋(CMAKE_BUILD_TYPE=Release)은 CMake 기본값이라 /Zi도 /DEBUG도 없다. 실제로 돌릴 release 서버의 덤프는 BaseTests+0x1c57처럼 주소만 나온다.

후

CMAKE_MSVC_DEBUG_INFORMATION_FORMAT ProgramDatabase(= /Zi) + release 링크 /DEBUG /OPT:REF /OPT:ICF. 최적화(/O2)는 그대로다. /DEBUG가 기본으로 끄는 링크 최적화 두 개만 다시 켠다. release 덤프에서 함수 이름과 줄 번호가 나오는 것을 확인했다.

바로잡음: C# 크래시 덤프 이름

CrashDump.cs 주석에 "이름 규칙은 C++과 같게"라고 적었는데, 실제 파일은 DeadlockDump.exe_1795774681_pid44500_crash.dmp였다. %e는 .exe까지 붙고 %t는 날짜가 아니라 1970년부터 센 초다. createdump에는 날짜 형식이 없어 같게 만들 수 없다. 주석을 고쳤다(bf66323). 수동 덤프(CrashDump.Write)는 이름을 우리가 만들어서 C++과 같다.

데드락 찾는 법

확인용으로 서로 반대 순서로 뮤텍스 두 개를 잡는 스레드 두 개를 만들고, 1초 뒤 살아 있는 상태로 수동 덤프를 남겼다.

C++ std::mutex

~*kn에서 RtlAcquireSRWLockExclusive(뮤텍스 잡기)에 멈춘 스레드를 찾는다. 그 위 프레임이 어느 함수 몇 번 줄에서 무엇을 잡으려는지 보여 준다.

5  ntdll!RtlAcquireSRWLockExclusive
   std::_Mutex_base::lock
   SaveInventoryThenGuild   [DeadlockDump.cpp @ 20]
6  ntdll!RtlAcquireSRWLockExclusive
   std::_Mutex_base::lock
   UpdateGuildThenInventory [DeadlockDump.cpp @ 27]

주인: 변수를 알면 x 모듈!*g_inventory*(natvis가 locked로 보여 준다) → dt -r4 std::mutex <주소>의 _Thread_id. 아래 "바로잡음" 참고.

C# lock

!syncblk가 lock마다 주인 스레드를 바로 보여 준다. !clrstack -all에서 Monitor.Enter에 멈춘 스레드와 맞춰 보면 된다.

    1           3 f18   8        System.Object

MonitorHeld 3 = 주인 1 + 기다리는 스레드 하나(2). 두 lock이 서로의 주인을 기다리면 데드락이다.

바로잡음: lock 주인은 C++에서도 보인다 (2026-11-27)

처음에 "std::mutex는 주인 스레드를 기록하지 않는다"고 적었다. 같은 덤프를 다시 열어 보니 틀렸다. OS의 SRW lock은 주인을 적지 않지만, MSVC std::mutex는 그 바깥에 잡은 스레드 id를 따로 적는다. 크리티컬 섹션(CRITICAL_SECTION)도 같은 프로그램으로 바꿔 확인했다.

   +0x008 _M_srw_lock : 0x0000008a`b79ffa13   ← SRW lock: 잠김 비트 + 기다리는 스레드 쪽 포인터, 주인 없음
   +0x048 _Thread_id  : 0n16308              ← 0x3FB4 = 스레드 5 SaveInventoryThenGuild
   +0x04c _Count      : 0n1

!locks                                     (CRITICAL_SECTION 판)
CritSec DeadlockCs!g_inventoryCs  OwningThread 52e0  LockCount 1  ContentionCount 1
CritSec DeadlockCs!g_guildCs      OwningThread 500c  LockCount 1  ContentionCount 1
Scanned 6 critical sections
lock주인을 어디에 적나덤프에서 찾는 법변수 이름 없이 전부 훑기
SRWLOCK(OS, 맨 것)적지 않는다. 8바이트에 잠김·기다림 비트와 기다리는 스레드 쪽 포인터만. 공유 모드(여럿이 동시에 쥠)가 있어 주인 하나를 둘 수 없다스택을 보고 추론❌
std::mutex(MSVC)SRW lock 옆 _Thread_id, _Count. 같은 스레드가 두 번 잡는 실수를 검사하려고 둔 것(표준이 아니라 MSVC 구현)dt std::mutex <주소>❌ 변수를 알아야 한다
CRITICAL_SECTIONOwningThread, RecursionCount(재귀 허용). 만들 때 디버그 정보를 ntdll 전역 목록에 이어 둔다!locks(ntdll 심볼 필요 → MS 심볼 서버)✅ 잡힌 것 전부
C# lock(Monitor)경합이 없으면 객체 헤더(thin lock)에 스레드 id, 경합이 생기면 런타임의 SyncBlock 표!syncblk(경합 있는 것), !dumpheap -thinlock(헤더에만 있는 것)✅ 런타임 표를 훑는다

그래서 데드락 분석이 편한 순서는 크리티컬 섹션 ≈ C# lock > std::mutex > 맨 SRW lock이다. 크리티컬 섹션과 C#은 디버거가 "잡힌 lock 전부"를 훑어 주고, std::mutex는 주인이 적혀 있지만 어느 변수인지 먼저 알아야 한다.

  • 범위: 확인한 것은 전역 변수 lock이고, Mini 덤프에도 들어 있었다(데이터 구역 포함). 힙 객체 안의 lock은 Mini에 안 들어갈 수 있다. 그때는 Full 덤프로 본다(확인 안 함).
  • 지금 코드: 그대로 std::mutex를 쓴다. Lane 구조(스레드가 자기 큐만 처리)에서는 lock을 겹쳐 잡는 곳이 거의 없고, 주인도 덤프에 남는다. 실제로 데드락을 겪으면 그때 다시 본다.

확인용 프로그램(커밋하지 않음)

다시 확인하고 싶을 때 쓰는 코드다. Base.lib에 링크해 VS 개발자 환경에서 컴파일한다.

std::mutex g_inventory;
std::mutex g_guild;

void SaveInventoryThenGuild()
{
    std::scoped_lock first{g_inventory};
    std::this_thread::sleep_for(200ms);
    std::scoped_lock second{g_guild};        // 여기서 영원히 기다린다
}
void UpdateGuildThenInventory()              // 반대 순서
{
    std::scoped_lock first{g_guild};
    std::this_thread::sleep_for(200ms);
    std::scoped_lock second{g_inventory};
}

int main()
{
    Base::CrashDump::Install({.directory = "dumps"});
    std::thread a{SaveInventoryThenGuild}, b{UpdateGuildThenInventory};
    std::this_thread::sleep_for(1s);
    Base::CrashDump::Write(Base::DumpKind::Full, "deadlock");   // 스냅샷
    std::quick_exit(0);                                         // 데드락 스레드는 join 할 수 없다
}

// cl /std:c++latest /EHsc /Zi /MDd /utf-8 /I server-cpp/Core DeadlockDump.cpp /link server-cpp/build/debug/Base.lib dbghelp.lib

서버가 죽거나 멈췄을 때 순서

  1. 죽었다: dumps/에서 _crash·_terminate·_abort·_purecall·_invalidparameter 덤프를 찾는다. C++은 .ecxr → kn, C#은 !pe.
  2. 멈췄다(응답 없음): 프로세스를 죽이기 전에 수동 덤프(CrashDump::Write, 나중에 관리 콘솔)를 남긴다. C++은 ~*kn, C#은 !syncblk → !clrstack -all.
  3. 메모리가 계속 는다: Full 덤프. C#은 !dumpheap -stat.
  4. 그 빌드의 exe·pdb를 심볼 경로에 넣는다. 빌드가 다르면 줄 번호가 틀린다.
