개발일지 · 스레드 구조

설계 논의 · 2026-11-27 · 서버 구조(결정 001: 분산 존) 위에서 프로세스 안 스레드를 어떻게 나누나. 초안이다. 확정되면 결정 005로 옮긴다

한 줄 요약. 스레드는 기능(전투, 길드, 브로드캐스트…)이 아니라 멈추는 성질로 세 풀만 둔다: IO 커널 대기, Logic CPU만(멈추면 안 됨), Blocking DB·파일 대기. 기능은 스레드가 아니라 데이터의 주인(Lane)으로 나눈다. 게임 데이터는 주인 Lane 하나만 만지므로 lock이 없다.

1. 원칙 네 가지

#원칙뜻
①스레드는 멈추는 성질로 나눈다IO(소켓 완료를 기다림) · Logic(기다리지 않고 계산만) · Blocking(DB·파일을 기다림). 콘텐츠가 늘어도 풀은 세 개다
②데이터마다 주인 Lane은 하나존의 월드와 그 존 플레이어 = 존 Lane. 길드 = 길드 Lane(ServiceServer). 다른 스레드는 주인에게 메시지로 부탁만 한다
③결과는 항상 주인에게 다시 PostDB 저장 완료, 다른 서버의 답, 타이머 모두 주인 Lane으로 돌아온다. 콘텐츠 코드는 언제나 주인 스레드에서만 돈다
④Logic 스레드는 절대 기다리지 않는다DB, 파일, sleep, 다른 Lane의 답을 기다리는 lock 금지. 기다릴 일은 Blocking 풀이나 다른 서버에 보내고 ③으로 결과를 받는다

2. ZoneServer 안 (8코어 예)

패킷은 IO 스레드가 받아 자르고 역직렬화한 뒤, 그 플레이어가 있는 존 Lane에 넣는다. 존 Lane이 틱과 콘텐츠를 모두 처리하고, 틱 끝에 보낼 패킷을 세션별로 묶어 IO에 넘긴다.

  • Logic 풀 = 존 Lane들. 존 수와 스레드 수를 따로 정한다. 존은 만들 때 LaneGroup.At(index)로 Lane 하나에 고정한다(존 이동이 없는 한 바뀌지 않는다).
  • IO 스레드는 게임 데이터를 만지지 않는다. 바이트를 메시지로 바꿔 주인 Lane에 넣는 데까지만 한다(결정 004).
  • Blocking 풀이 ZoneServer에는 없다. DB는 DbWriter 프로세스에 보낸다(원칙 ④).

3. 존 Lane 하나가 하는 일: 틱도 메시지다

존 Lane의 큐에는 패킷 메시지와 Scheduler가 50ms마다 넣는 Tick 메시지가 섞여 들어온다. 같은 스레드가 차례로 처리하므로 lock이 없다.

브로드캐스트 스레드를 따로 두지 않는 이유

월드 상태의 주인은 존 스레드다. 다른 스레드가 브로드캐스트하려면 월드를 복사하거나 lock을 걸고 읽어야 한다. 틱 끝에 주인이 직접 세션별 묶음을 만들면 둘 다 필요 없다. 보내기 자체(WSASend)는 비동기라 존 스레드는 넘기고 바로 다음 일을 한다.

틱 스레드를 따로 두지 않는 이유

틱이 메시지라서 존 수와 스레드 수가 묶이지 않는다. 존 100개를 Lane 8개에 나눠 담을 수 있다. 패킷 처리와 틱이 같은 스레드라 입력 목록에도 lock이 없다. 이 방식이 결정 004에 남겨 둔 "A. 틱을 Lane의 일로"이다.

입력이 몇 번 와도 같은 처리: 전용 스레드 없이 어떻게 하나

전용 TICK·BROADCAST 스레드를 둔 서버에서 그 스레드들이 지켜 주던 것은 이것이다: 클라이언트가 한 틱 사이에 입력을 몇 번 보내든, 처리는 틱마다 한 번, 같은 틱 시각으로, 브로드캐스트도 틱마다 한 번. 이 성질은 스레드가 아니라 "입력을 쌓았다가 틱에서 한 번에 처리"에서 나온다. 이번 구조는 그것을 존 Lane 하나 안에서 한다.

입력 종류입력 목록에 쌓는 법틱에서
이동덮어쓰기: 플레이어마다 마지막 하나지난 틱 위치 → 새 위치를 속도·지형으로 검사하고 한 번 적용
스킬·공격차례로 쌓기: 행동 하나하나가 의미 있음쿨타임·공용 쿨타임으로 거르고, 같은 틱 시각으로 판정
같은 요청을 여러 번(연타, 재전송)요청 번호로 중복 버리기한 번만 처리
인벤토리·채팅처럼 월드 밖쌓지 않음도착하면 바로(틱과 상관없는 결과)

정리하면 그 서버의 TICK 스레드가 하던 "모았다가 틱에서 한 번", BROADCAST 스레드가 하던 "틱마다 한 번 보내기"를 존 Lane 안의 입력 목록과 Tick 메시지의 ④단계가 한다. 성질은 같고, 다른 것은 스레드를 넘나들지 않는다는 점이다.

전용 틱·브로드캐스트 스레드와 비교 (나중에 실측)

이번 구조(존 Lane 하나)전용 TICK + BROADCAST 스레드

"한 주인으로 복사·lock을 없애는 것이 더 이득"이라는 가설이다. 같은 Core·같은 봇 시나리오로 서버 레이어만 바꿔 재 본다(PROGRESS "구조 비교 ①", 1단계 끝). 틱 시작 지연 p99나 브로드캐스트 비율이 기준을 넘으면 8장의 대책 → 전용 스레드 순으로 바꾼다.

4. 기다려야 하는 일: 결과는 주인에게 돌아온다

예: 아이템 구매(재화 = 즉시 트랜잭션). 존 Lane은 DB를 기다리지 않는다. 요청을 보내고 다음 일을 하다가, 결과가 오면 같은 Lane에서 이어서 처리한다.

기다리는 동안 그 플레이어의 다른 구매는 "진행 중"으로 막거나 차례로 쌓는다. 이 규칙은 콘텐츠마다 정한다. 다른 서버(ServiceServer의 길드)에 묻는 것도 같은 모양이다.

  • Logic 안의 Lane 고르기: Zone은 At(index)(존 고정), ServiceServer는 LaneFor(guildId)(키 해시).

7. C#에서는

C++
  • IO: IOCP 스레드 직접(GetQueuedCompletionStatus)
  • Logic: LaneGroup(Lane = 전용 스레드)
  • Blocking: 전용 스레드 + ODBC(DbWriter)
  • Tick: Scheduler::Every(50ms, zoneLane, …)
C#
  • IO: Socket 비동기 + System.IO.Pipelines(런타임 IOCP 스레드 풀)
  • Logic: 우리 LaneGroup(Channel + 전용 스레드). 스레드 풀이 아니라 전용 스레드라 틱이 풀 혼잡에 밀리지 않는다
  • Blocking: 필요 없음. DB는 async(Dapper + await)라 기다리는 스레드가 없다
  • 주의: await 뒤 코드는 아무 풀 스레드에서 이어진다. 원칙 ③을 지키려면 이어지는 곳을 주인 Lane으로 돌려야 한다(Lane용 SynchronizationContext 또는 결과를 Post). 만들 때 정한다

8. 대가와 깨지는 조건

약점보이는 증상(측정)대책
같은 Lane의 무거운 존이 옆 존 틱을 늦춘다틱 시작 지연 p99, 틱 시간존 배치 바꾸기, 무거운 존은 Lane 혼자. 그래도 안 되면 Lane을 "가벼운 큐"로 바꿔 한가한 스레드가 가져가게(strand 방식)
브로드캐스트가 틱을 많이 먹는다틱 안 ④단계 시간④를 AOI 셀별로 Logic 풀에 잠깐 펼쳤다 모으기(fork-join). 스레드 그룹은 늘리지 않는다
한 존이 스레드 하나로 모자람Lane 혼자인데도 틱 50ms 초과존을 쪼갠다(채널 존). 정말 한 맵이어야 하면 그 전장만 공간 분할(결정 001)
요청-결과 방식이라 코드가 길어진다콘텐츠 코드 리뷰C++ 코루틴이나 C# await로 "보내고 이어서"를 한 함수처럼 쓰기(이어지는 곳은 주인 Lane)
