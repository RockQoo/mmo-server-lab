개발일지 · CodeGen 검토

CodeGen · 2026-11-28 · 언제 만들지, 스키마 형식, 생성 방식, 프로토콜 파일 나누기, 패킷 ID 대역, 처리 위치. 결론: 지금은 만들지 않는다. Core를 먼저 만들고 프로토콜은 손으로 쓰다가, 쌓이면 이 문서의 후보로 다시 검토한다

한 줄 요약. CodeGen이 만든 코드를 쓸 곳(1단계 게임 메시지)이 아직 없고, 패킷 ID·머리 모양은 Network 단위에서 정해진다. 먼저 만들면 짐작으로 설계하게 된다. 그래서 개발 순서에서 CodeGen을 빼고 Config → Network로 가며, 패킷은 손으로 쓴다. 아래는 그때 다시 꺼낼 확정 후보다(아직 결정 아님).

1. 왜 지금 만들지 않나

  • 쓸 곳이 없다. 생성된 메시지는 1단계 게임 레이어(접속 → 로그인 → 존 입장 → 이동)에서 처음 쓰인다. Network Core는 메시지 종류를 모르고 바이트와 패킷 머리만 다룬다.
  • Network 결정에 기댄다. CodeGen은 구조체뿐 아니라 패킷 ID와 그 규칙을 만든다. 패킷 머리(크기, ID 위치)는 Network에서 정해진다.
  • 쓰는 곳 없이 기능을 늘리면 필요 없는 기능까지 만든다. 손으로 쓴 패킷이 쌓이면 무엇을 생성해야 하는지가 실제 코드로 보인다.

다시 검토할 때

  • 손으로 쓴 패킷이 늘어 C++·C# 두 벌을 맞추는 일이 반복될 때(두 벌이 어긋난 버그가 한 번이라도 나면 바로)
  • UE5 클라이언트가 붙을 때(세 번째 벌이 생긴다)
  • 기획 데이터 표(아이템, 스킬)가 생길 때

그 전까지 손으로 쓴 패킷은 testdata/bytes/ 정답 파일로 C++·C#이 같은 바이트를 내는지 검사한다(지금 Base 테스트와 같은 방식).

3. 스키마 형식: JSON으로 통일 (후보)

처음엔 직접 만든 문법, 다음엔 YAML을 생각했다. 그런데 Config는 이미 JSON이고, 데이터 파서는 하나로 맞추는 것이 목적이라 형식을 하나로 정한다. 기준은 docs/libraries.md의 외부 라이브러리 기준(C++ 스타 1만 이상, C# 다운로드 1억 이상)을 두 언어 모두 넘는가다.

  • 필드는 배열로 적는다. 배열 순서 = 바이트 순서. 객체({})는 순서를 보장하지 않는다(nlohmann 기본 json은 키를 정렬한다).

4. 생성 방식: C# 원시 문자열 + IndentedTextWriter (후보)

방법판단
Scriban(텍스트 템플릿)템플릿이 결과와 닮아 보기 좋다. 그러나 템플릿 오타가 실행해야 드러나고, 다운로드 약 6,280만으로 기준 미달
T4예전 기술, .NET에서는 비공식 포팅 필요
Roslyn Source GeneratorC#만 만든다. C++·UE 출력이 안 된다
C# 원시 문자열($$""") + BCL IndentedTextWriter설치 없음. 이름·타입을 틀리면 컴파일 에러, 디버거로 따라간다. $$를 쓰면 C++의 {를 그대로 쓰고 {{값}}만 끼워 넣는다
  • 출력마다 생성기를 따로 둔다(CppGenerator, CsGenerator, 나중에 UE).
  • 생성 뒤 clang-format / dotnet format을 돌려 lint를 그대로 통과시킨다. 작은 스키마의 생성 결과를 정답 파일과 비교하는 테스트를 처음부터 둔다.
  • 다시 생각할 때: 출력이 크게 늘 때, 코드를 모르는 사람이 출력 모양을 고쳐야 할 때.

5. 프로토콜 파일과 패킷 ID (후보)

파일을 나누는 목적은 "누가 알아야 하는가"로 생성 대상을 고르는 것이다. 서버끼리 쓰는 패킷은 클라이언트에 생성하지 않는다(클라이언트 실행 파일에 서버 내부 프로토콜이 남지 않는다).

proto/
  enums.json, types.json, constants.json   공통
  protocol/
    client_server.json      클라 ↔ 서버(클라가 붙는 곳은 Gateway 하나). 묶음마다 분류 번호
    server/
      gateway_zone.json     연결 하나에 파일 하나, 양쪽 서버에만 생성
      zone_service.json
  data/                     기획 데이터 정의
  targets.json              출력마다 어떤 파일을 생성할지
  • 분류 번호는 묶음 맨 위에 직접 적는다. 묶음을 추가하거나 이름을 바꿔도 기존 번호가 흔들리지 않는다.
  • 묶음 안 번호는 순서대로 자동. 중간에 끼워 넣어 번호가 밀려도 접속 때 프로토콜 해시 비교로 버전이 다른 클라이언트는 끊긴다.
  • 대역(분류를 어떻게 나눌지)은 서버↔서버 패킷이 적을 것이라 더 검토가 필요하다.

6. 처리는 각 프로세서의 Dispatcher가 (후보)

프로토콜에는 "어디와 어디 사이"만 적고, 처리하는 서버(handler)는 적지 않는다. 각 서버가 처리할 패킷을 코드에서 등록한다. 정보가 등록 코드 한 곳에만 있어 스키마와 서버 구성이 어긋날 일이 없다.

dispatcher.Register<MoveReq>(OnMove);      // ID 는 생성된 MoveReq::Id 에서
dispatcher.Register<AttackReq>(OnAttack);
dispatcher.Dispatch(packet);                 // ID 로 표를 찾아 맞는 함수를 부른다
이름고르는 것우리 구조
Dispatcher(배차 담당: 종류를 보고 맞는 곳에 배정)같은 곳 안에서 어떤 함수를 부를지각 프로세서의 PacketDispatcher(결정 004)
Router어느 곳(서버, 프로세서, Lane)으로 보낼지MessageRouter(2단계), Gateway 세션별 경로표
  • Gateway가 어느 서버 종류로 넘길지는 뒤쪽 서버가 접속할 때 "나는 이 분류를 처리한다"를 알려 Gateway가 표를 만드는 방식이 후보다. 어느 인스턴스로 보낼지는 세션별 경로표(실행 중에 바뀐다).
  • 아무도 등록하지 않은 클라이언트 패킷은 시작 때나 테스트에서 찾아 알린다.
  • 확정은 Network 단위에서 한다.
