1. 측정 도구가 여러 스레드 결과를 눌렀다

Google Benchmark DoNotOptimize와 true sharing

2026-11-26 · 자세히: benchmark.html
증상아무 일도 안 하는 반복(Noop)이 스레드 1개 627M/s → 8개 735M/s. 8코어인데 1.2배만 늘었다
원인반복마다 부른 benchmark::DoNotOptimize()가 MSVC에서 전역 변수 하나에 쓴다. 8개 스레드가 같은 캐시 줄(64B)에 써서 줄이 코어 사이를 계속 오갔다
해결스레드마다 자기 volatile 변수에 쓰게 바꿨다. "Noop을 먼저 재고, 스레드 수만큼 늘지 않으면 결과를 믿지 않는다"를 규칙으로 만들었다
결과BufferPool 2판 8스레드 값이 1,655M/s로 정상이 됐다. 그 전에 잰 여러 스레드 값은 모두 다시 쟀다

30초 답변. 여러 스레드 벤치마크가 이상하게 안 늘어서, 아무 일도 안 하는 Noop부터 쟀습니다. 표준 C++만으로 만든 Noop은 7배 늘고 벤치마크 도구 안의 Noop만 안 늘어서, 도구의 DoNotOptimize가 MSVC에서 전역 변수 하나에 쓴다는 걸 찾았습니다. 모든 스레드가 같은 캐시 줄을 쓰는 true sharing이었고, 스레드별 변수로 바꿔 해결했습니다. 그 뒤로는 Noop 기준선을 먼저 확인하고 결과를 봅니다.

2. BufferPool 1판이 new/delete보다 느렸다

등급마다 mutex 하나 → 스레드 캐시 + 전역 묶음

2026-11-26 · 자세히: bufferpool.html, 보고서 007·008
증상풀을 썼는데 스레드 1개에서도 new/delete(48M/s)보다 느렸다(33M/s). 스레드가 늘수록 더 느려졌다
원인빌리기·반납마다 mutex 잠금·풀기 + 원자 카운터 = 원자 연산 6번(약 30ns). Windows 힙은 작은 크기를 스레드별로 처리해 19ns. 풀이 아끼는 비용보다 더하는 비용이 컸다
해결2판: 스레드마다 캐시(락 없음)를 두고, 넘치거나 빌 때만 전역에 묶음으로 넣고 꺼낸다. mutex는 묶음 하나에 한 번. C# ArrayPool과 같은 구조
결과스레드 1개 33M → 223M/s(약 6.8배), C# ArrayPool(268M/s)과 같은 급. 8스레드 1,655M/s(new/delete의 약 7배)

30초 답변. 처음 만든 버퍼 풀은 등급마다 mutex 하나였는데, 재 보니 new/delete보다 느렸습니다. 원자 연산 수를 세 보니 빌리고 반납하는 데 6번, 약 30ns였고 Windows 힙은 19ns였습니다. 그래서 스레드별 캐시를 두고 전역은 묶음 단위로만 만나게 바꿨고, 스레드 1개에서 6.8배, C# ArrayPool과 같은 급이 됐습니다.

3. 빌리는 스레드 ≠ 반납하는 스레드에서 무너졌다

4. C# 공식 풀이 스레드를 늘리면 느려졌다

C++ ObjectPool vs C# DefaultObjectPool vs C# new

2026-11-26 · 자세히: objectpool.html, 보고서 009
질문C#은 풀을 공식으로 준다(Microsoft.Extensions.ObjectPool). C++로 직접 만든 풀은 최소한 그만큼은 나와야 한다
원인 분석C# DefaultObjectPool은 스레드별 캐시가 없다. 모든 스레드가 배열 하나를 Interlocked로 다툰다. 그래서 스레드가 늘수록 느려진다(102M → 15M/s)
C++ 설계BufferPool 2판과 같은 스레드 캐시 + 전역 묶음. 반납 때 소멸하지 않고 Reset()만 해서 내부 vector 용량까지 다시 쓴다
결과C++ 풀 845M → 3.01G/s. C# 풀보다 1스레드 약 8배, 8스레드 약 200배. C# new(479M → 1.96G)보다도 빠르다

배운 것: C#의 new는 포인터를 앞으로 미는 것뿐이라 아주 싸고, 짧게 사는 객체는 Gen0에서 거의 공짜로 치워진다. 그래서 C#은 만들기 비싼 객체만 풀에 넣는다. C++은 할당기가 비싸서 풀이 크게 이긴다.

30초 답변. C# 공식 오브젝트 풀을 재 보니 스레드를 늘릴수록 느려졌습니다. 스레드별 캐시 없이 공유 배열 하나를 Interlocked로 다투기 때문입니다. C++은 스레드 캐시와 전역 묶음 구조로 만들어 8스레드에서 약 200배 빨랐습니다. 반대로 C#은 GC 할당 자체가 싸서, 작은 객체는 풀 없이 new하는 게 맞다는 결론도 같이 얻었습니다.

6. C#·C++ 측정 틀이 공정하지 않았다

Parallel.For, 측정마다 스레드 만들기 → ThreadTeam

2026-11-26 · Codex 리뷰 1~3차 · 자세히: objectpool.html
증상C#은 Parallel.For, C++은 측정마다 스레드를 새로 만들었다. Noop이 8스레드에서 C++ 3.8배, C# 3.4배만 늘었다
원인① MaxDegreeOfParallelism은 상한일 뿐이라 실제로 동시에 도는 스레드 수를 보장하지 않는다. ② 측정 한 번이 몇 ms라 스레드 생성 비용과 출발 시차(앞 스레드가 먼저 시작)가 섞였다
해결두 언어 모두 같은 틀: 스레드를 측정 밖에서 미리 만들고 barrier로 같이 출발, 같이 끝(Bench/ThreadTeam). 스레드 생성 실패 때 멈추는 문제도 고쳤다
결과Noop 8스레드 C++ 4.7배, C# 5.2배. 아직 8배는 아니다(64B 정렬은 같고 코어 고정은 더 느림). 그래서 "스레드 몇 배" 결론은 쓰지 않고 같은 스레드 수끼리 언어 비교만 한다

30초 답변. C#과 C++을 비교하려면 측정 방법부터 같아야 했습니다. Parallel.For는 동시 스레드 수를 보장하지 않고, 측정마다 스레드를 만들면 생성 비용과 출발 시차가 섞였습니다. 그래서 미리 만든 스레드를 barrier로 같이 출발시키는 틀을 두 언어에 똑같이 만들었습니다. 이 틀도 8코어에서 5배까지만 늘어서, 결론은 같은 스레드 수에서의 비교로만 냅니다.

11. Lane이 보장하는 것: 같은 ID는 순서대로, 락 없이

설계 결정 · Lane을 만든 목적과 큐 후보의 기준

2026-11-27 · 자세히: messagequeue.html, 결정 003
목적아무 스레드나 일을 처리하면 도착 순서가 보장되지 않는다. ID를 정해 늘 같은 스레드(Lane)에서 처리하면 그 ID의 일은 순서대로, 락 없이 돈다(asio strand와 같은 순서 보장 + 스레드 고정)
분석"넣은 순서"의 뜻이 큐마다 다르다. 생산자마다 작은 큐를 두는 ConcurrentQueue는 스레드가 다르면 먼저 끝난 Post보다 나중 것이 먼저 실행될 수 있다
결정보장 = 같은 Lane에 넣은 일은 Post가 끝난 순서대로 하나씩 실행(넣은 스레드가 달라도). ConcurrentQueue는 후보에서 뺀다. 묶어 넣기는 "내보낸 뒤에만 다음 일을 일으킨다"를 지킬 때만
콘텐츠 규칙① 남의 ID 데이터는 직접 만지지 않고 메시지로 ② 답을 기다리지 않고 메시지로 받는다 ③ 실패하면 되돌린다 ④ 경쟁하는 요청은 한 명만 이기면 된다

길드 재료는 길드 100 Lane만 만지므로 락이 없다. A와 B 중 누가 먼저인지는 정해져 있지 않아도 된다(둘 다 맞다). 중요한 것은 한 명만 이긴다는 것이고, 그것을 길드 Lane이 하나씩 처리해서 보장한다. C#의 길드·파티 서버에 쓸 Microsoft Orleans의 grain(ID마다 한 번에 메시지 하나)과 같은 생각이다.

30초 답변. 플레이어나 길드처럼 ID가 있는 데이터는 ID를 섞어서 고른 Lane, 즉 전용 스레드 하나에서만 만지게 했습니다. 그래서 콘텐츠 코드에 락이 없습니다. 다른 ID의 데이터가 필요하면 그 Lane에 메시지를 보내고 답도 메시지로 받습니다. 예를 들어 길드 재료가 하나 남았을 때 두 명이 동시에 사면, 길드 Lane이 요청을 하나씩 처리해서 한 명만 성공하고 다른 한 명은 예약했던 재화를 돌려받습니다. 큐는 Post가 끝난 순서대로 실행된다는 보장이 필요해서, 생산자별 큐를 쓰는 ConcurrentQueue는 후보에서 뺐습니다.

12. 패킷 흐름과 MessageRouter

설계 결정 · 패킷이 Processor까지 가는 길, 다른 Processor로 보내는 법

2026-11-27 · 자세히: 결정 004
MessageRouter 사용법 후보모양판단
A. Processor를 템플릿으로router.Post<GuildProcessor>(guildId, msg)목적지가 보인다. 키·메시지 실수를 못 막는다
B. 종류를 enum으로router.Post(ProcessorKind::Guild, guildId, msg)다른 서버에도 쓴다. 실행 중에만 검사
C. 키 타입이 목적지router.Post(guildId, msg)간결하지만 목적지가 코드에 안 보인다
① A + B (채택)router.Post<GuildProcessor>(guildId, msg) + GuildProcessor::Kind쓰는 모양은 A, 안쪽은 enum. 키 타입(P::Key)과 On(msg)를 컴파일 때 검사(실행 비용 0). 실행은 배열 한 칸 + LaneFor + Lane::Post

성능 확인 계획: 만들 때 "Lane에 바로 Post" vs "MessageRouter로 Post"를 같은 벤치마크로 재서 더해지는 비용(예상: 몇 ns)을 여기에 적는다.

보충(2026-11-27): MessageRouter는 2단계(존 이동)에 만든다. 분산 존 구조(결정 001)에서 플레이어 데이터 주인은 Zone이고 길드는 ServiceServer(5단계, 다른 프로세스)에 있다. 그래서 ZoneServer에서 Post<GuildProcessor>는 다른 서버로 보내기다. 1단계 ZoneServer 안의 Processor는 사실상 ZoneProcessor 하나라 보낼 곳이 없다(입구는 PacketDispatcher, 같은 존 안은 직접 호출). 첫 실제 사용처는 존↔존(Post<ZoneProcessor>(targetZoneId, HandoffReq)).

30초 답변. 패킷은 IOCP 스레드들이 자르고 검사하고 역직렬화까지 한 뒤, 패킷 번호 표로 목적지 Processor와 키를 골라 그 Lane에 넣습니다. 수신 하나에 든 패킷은 Lane별로 묶어 한 번에 넣어 잠금 횟수를 줄였고, 다음 수신을 걸기 전에 내보내서 순서를 지킵니다. 처리 중에 다른 Processor가 필요하면 MessageRouter에 Processor 타입과 키를 넘기는데, 키 타입과 받는 메시지가 맞는지 컴파일러가 검사하므로 잘못 보내는 실수가 빌드에서 걸립니다.

14. 크래시 덤프: 크래시 난 스레드가 아니라 덤프 전용 스레드가 쓴다

덤프 뒤 남은 로그 flush (2026-11-27)

로그는 로그 Lane 큐에 쌓였다가 파일로 간다. 크래시 순간 큐에 남은 줄은 프로세스와 같이 사라진다. 한 줄에 1ms 걸리는 sink로 200줄을 넣고 바로 크래시 내면 flush 없이 3줄만 남았고, flush를 넣자 200줄이 모두 남았다.

  • C++: CrashDumpOptions.afterCrash = [] { Log::Flush(); }(Base는 Log를 모르니 서버가 함수 포인터로 넘긴다). 크래시 난 스레드가 아니라 덤프 전용 스레드가 부르고, 크래시 난 스레드는 afterCrashTimeout(기본 1초)까지만 기다린다. 크래시 난 스레드가 로그 Lane 자신이면 flush가 영원히 끝나지 않기 때문이다(테스트: 끝나지 않는 콜백 + 200ms 제한 → 0.27초에 종료).
  • C#: Logger.Initialize가 AppDomain.UnhandledException에 처리기를 건다. 예외를 Fatal 한 줄로 남기고 CloseAndFlush를 1초 제한으로 부른다. 처리기가 돌아오면 런타임이 덤프를 쓴다.

앞으로: 수동 덤프 명령은 Network 뒤 관리 콘솔(localhost·내부망만, 인증).

30초 답변. 크래시 덤프는 크래시 난 스레드가 직접 쓰지 않고 미리 만든 덤프 전용 스레드가 씁니다. 스택 오버플로처럼 크래시 난 스레드에 스택이 거의 없어도 덤프를 남길 수 있고, 그 스레드의 스택이 멈춘 그대로 덤프에 들어갑니다. 만들면서 MSVC의 terminate 처리기가 스레드마다 따로라는 걸 테스트로 확인해서, 다른 스레드의 terminate는 프로세스 전체에 걸리는 SIGABRT로 잡았습니다. 같은 경로로 살아 있는 서버도 죽이지 않고 덤프를 뜹니다. 다만 Full 덤프는 쓰는 동안 서버 전체가 멈춰서, 1GB에서 510ms였던 멈춤을 프로세스 스냅샷(copy-on-write 복사본)을 떠서 덤프하는 방식으로 21ms까지 줄였습니다.

C#에는 TimerHeap이 없다. C# Scheduler는 BCL TimeProvider.CreateTimer(런타임 타이머)에 맡기고 콜백은 Lane에 넣기만 한다. 주기 일의 다음 시각을 .NET 소스로 확인했다(2026-11-28, dotnet/runtime main).

C++ TimerHeap은 다음 칸으로 건너뛰어 원래 칸을 지킨다. 이 차이는 주기보다 길게 늦었을 때만 보인다.
  • 다시 예약은 콜백 전에 잠금 안에서 하고 콜백은 스레드 풀에서 돈다. 그래서 앞 콜백이 아직 돌아도 다음 콜백이 겹쳐 돌 수 있다. C# Scheduler의 콜백은 Lane에 넣기만 해서 겹쳐도 일은 Lane에서 하나씩 돈다.
  • 테스트용 FakeTimeProvider는 다르다(dotnet/extensions FakeTimeProvider.cs의 Advance → WakeWaiters): 시간을 먼저 다 옮긴 뒤 깨어날 일을 고르고, 주기 일은 WakeupTime += Period로 한 칸씩 올려 다시 고른다. 그래서 한 번에 주기 여러 개를 넘기면 놓친 주기마다 콜백이 한 번씩 연달아 불린다(실제 런타임은 한 번 + 1ms 뒤 한 번). 지금 테스트는 한 주기씩 넘겨 영향이 없다. 주기 여러 개를 한 번에 넘기는 테스트는 이 차이를 알고 써야 한다.

A. 풀 벤치마크를 N:M으로

다음 차례

풀의 CrossThread 측정은 지금 서로 독립된 1:1 쌍이다(빌리는 수 = 반납하는 수). 실무는 비율이 다르다. 생산자 4개가 빌리고 Lane 1개가 반납하면 Lane의 캐시는 늘 넘치고 생산자의 캐시는 늘 빈다. 거의 모든 호출이 전역 mutex를 거친다(사례 3의 압박이 더 세진다).

같은 스레드에서 빌리고 반납하는 SameThread 측정은 그대로 둔다(스레드 캐시 성능을 본다). C#에도 같은 N:M을 더해 C++과 비교한다.

B. Lane 큐 개선: 1.5배 느린 것을 C# Channel 수준으로

1단계 완료 · lock-free 보류

1단계: 원인 확정 ✅(2026-11-27). 사례 8의 가설 ①(stop 확인 → 잠금 안의 bool)과 ④(condition_variable_any → std::condition_variable)를 하나씩 고쳐 쟀다. 4:4 72.7 → 57.5ns, 8:4 73.3 → 59.6ns, 1:1 34.7 → 29.1ns. 1:1 합격선은 넘었고 4:4·8:4는 아직 밖이라 2단계로 간다(사례 8).

2단계: 구조 후보 비교 — A(메모리 배치) ✅, C(티켓 링 버퍼) 보류(2026-11-27, 사례 8 마무리). 같은 N:M 벤치마크에 넣는다. 합격선은 4:4·8:4에서 메시지당 45ns 이하, 1:1은 34ns 이하다. 모든 후보는 Lane의 순서 보장(사례 11: Post가 끝난 순서대로)을 지켜야 한다. 그래서 B는 뺐고 C는 조건부다.
