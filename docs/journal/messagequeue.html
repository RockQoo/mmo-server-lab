개발일지 · 메시지 큐

Messaging · 2026-11-27 · 큐에 객체를 넣을까 직렬화한 바이트를 넣을까, 생산자 N → 소비자 M에서 C++ Lane vs C# Channel<T>

한 줄 요약. 같은 프로세스 안에서는 객체를 넘긴다(C++은 ObjectPool과 함께). 바이트는 큰 메시지에서 3~13배 느렸다. 그런데 실무 모양(N:M)으로 재 보니 진짜 문제는 메시지가 아니라 C++ Lane 큐였다. Lane이 늘수록 느려져서 C# Channel보다 약 1.5배 느렸다. 두 큐 모두 넣을 때마다 잠금을 잡으므로(.NET 소스로 확인), 차이는 잠금 안에서 하는 일에 있다. 다음 단위에서 원인을 하나씩 확정하고 고친다(합격선 45ns).

결정 기록: 002 · 모음: 최적화·결정 노트 사례 7~10 · 코드: server-cpp/Bench/MessageQueueBench.cpp, server-cs/Bench/MessageQueueBench.cs

질문: 큐에 무엇을 넣나

측정 틀: 실무 모양을 흉내 내기

처음에는 생산자 1·4개 → Lane 1개만 쟀다. "1:4는 실무 데이터가 아니다, 경합이 훨씬 많을 것"이라는 지적을 받고 생산자 N → 소비자 M으로 바꿨다. 조합은 1:1, 4:1, 2:2, 4:2, 4:4, 8:4다(8:4는 12스레드라 물리 8코어보다 많다).

  • 끝 확인: C++은 Lane마다 "표시 일"을 마지막에 넣고 기다린다(넣은 순서대로 처리하므로 그게 끝나면 앞의 것도 끝). C# Channel에는 일을 넣을 수 없어 카운터가 보낸 수와 같아질 때까지 기다린다.
  • 생산자 스레드: 두 언어 모두 ThreadTeam(미리 만든 스레드 + barrier, 사례 6).
  • 처리: 모든 필드를 읽어 합친다. 네 방식이 같은 함수를 쓴다.

결과 1: 바이트는 큰 메시지에서 비싸다

큐를 빼고 한 스레드에서 "보내기 + 받기"만 이은 CPU 비용이다. 큐를 거친 값에는 깨우기 비용이 섞이므로(아래 "측정 함정"), 메시지 하나의 비용은 이 표로 본다.

왜 C++ Lane이 막히나

정말 잠금 대기인지 확인하려고 프로세스 전체의 CPU 시간을 user와 kernel로 나눠 쟀다(GetProcessTimes). kernel이 크면 깨우기(OS 호출)가 원인이고, user가 크면 잠금을 잡으려고 도는 시간과 캐시 줄 대기가 원인이다.

1:164ns5ns1.3만

4:4에서 생산자는 한 번도 기다리지 않았는데(Lane이 충분히 따라옴) 모든 스레드가 user CPU를 가득 썼다. 깨우기가 아니라 잠금 경합과 캐시 줄 왕복 쪽이다.

바로잡음: "C#은 lock-free라서 빠르다"는 틀렸다

처음에는 C# Channel이 lock-free라서 빠르다고 적었다. .NET 소스(dotnet/runtime의 SingleConsumerUnboundedChannel.cs)를 확인해 보니 SingleReader = true 채널은 쓰기(TryWrite)마다 lock (SyncObj)를 잡고, 잠금 안에서 단일 생산자·단일 소비자 큐(SingleProducerSingleConsumerQueue<T>)에 넣는다. 잠금이 없는 것은 읽기(TryRead)의 빠른 길뿐이다. 두 언어 모두 넣을 때마다 잠금을 잡으므로, 차이는 잠금 안에서 하는 일과 주고받는 데이터에 있다.

C++ Lane::Post를 다시 보고 세운 가설이다. 다음 단위(Lane 개선)의 첫 단계에서 하나씩 바꿔 재서 확정한다.

① 일이 많은데 더 빨랐다(깨우기 비용)

첫 측정(생산자 1 → Lane 1)에서 Chat Pool(46ns)이 Move Pool(75ns)보다 빨랐다. Chat이 처리할 일이 더 많은데도 그렇다.

Lane이 빨리 끝내 큐가 비면 잠들고, 생산자는 다음에 넣을 때 깨워야 한다(notify_one). 처리가 느린 쪽은 큐가 덜 비어 깨우기가 줄어든다. 그래서 큐를 거친 값은 같은 조합 안의 순위로만 보고, 메시지 하나의 비용은 큐 없이 잰 값으로 본다.

② C# 람다 캡처가 몰래 할당했다

클로저를 쓰지 않는 Channel 경로인데도 메시지마다 48B가 할당됐다. 같은 반복 안에 지역 변수를 캡처하는 람다가 있기만 해도 컴파일러가 반복마다 캡처 객체를 만든다. 람다를 함수로 빼서 고쳤다(Codex 리뷰 R1). C# 큐만 1:1이 65 → 50ns가 됐다. 자세한 코드: 사례 9.

Lane이 지켜야 하는 것: ID별 순서 (2026-11-27 결정)

Lane을 만든 주된 목적은 속도가 아니라 순서다. 아무 스레드나 일을 가져가면 도착 순서가 보장되지 않는다. ID를 섞어 Lane을 고르면(LaneGroup) 같은 ID는 늘 같은 Lane, 즉 같은 스레드 하나에서 넣은 순서대로 돈다. 그래서 그 ID의 데이터(플레이어, 길드)는 락 없이 만진다.

"넣은 순서"의 정확한 뜻

같은 Lane에 넣은 일은 Post가 끝난 순서대로 하나씩 실행된다. 넣은 스레드가 달라도 그렇다. 이게 왜 중요한지는 IOCP 수신에서 보인다. 한 세션의 패킷은 수신을 하나씩 걸기 때문에, 패킷1의 Post가 끝난 뒤에야 패킷2가 다른 스레드에서 들어온다.

그래서 ConcurrentQueue는 Lane 큐 후보에서 뺐다. 생산자가 모았다가 한꺼번에 넣는 방식도, 모아 둔 채로 다음 수신을 걸면 같은 이유로 뒤집힌다. "내보낸 뒤에만 다음 일을 일으킨다"를 지킬 수 있는 곳에서만 쓴다.

콘텐츠에서는: 길드 재료 구매

길드 재료가 1개 남았을 때 플레이어 A와 B가 동시에 산다. 재화는 각 플레이어 Lane에, 재료는 길드 Lane에 있으니 메시지를 주고받는다. 그림은 최적화·결정 노트 사례 11에 있다.

규칙왜
남의 ID 데이터는 직접 만지지 않고 그 Lane에 메시지로 요청한다직접 만지면 두 스레드가 같은 데이터를 쓰게 되어 다시 락이 필요하다
답을 기다리지 않는다. 답은 메시지로 받는다기다리면 Lane 하나가 묶이고, 서로 기다리면 교착(deadlock)이 생긴다
먼저 예약하고, 실패하면 되돌린다(재화 환불)두 Lane에 걸친 일은 한 번에 끝낼 수 없다. 한쪽은 되돌리는 처리가 필요하다
A와 B 중 누가 이길지는 정하지 않는다동시에 넣은 요청은 어느 쪽이 먼저여도 맞다. 한 명만 이기는 것을 길드 Lane이 보장한다
