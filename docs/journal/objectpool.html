개발일지 · ObjectPool

Memory · 2026-11-26 · 만들기 전의 질문과 결정, C++ ObjectPool vs C# DefaultObjectPool 측정

한 줄 요약. 객체를 소멸시키지 않고 반납할 때 Reset()만 해서 다시 쓴다(내부 vector 용량까지 재사용). 구조는 BufferPool 2판(스레드 캐시 + 전역 묶음)과 같다. C++ 풀은 스레드 1개에서 C# DefaultObjectPool보다 약 8배, 8개에서 약 200배 빠르고, GC 할당(C# new)보다도 빠르다.

질문 1: BufferPool이 큰 개념이고 ObjectPool이 그 아래인가?

위아래가 아니라 형제다. 굳이 층을 따지면 BufferPool이 아래(날 바이트), ObjectPool이 위(타입이 있는 객체)다.

BufferPoolObjectPool
다루는 것타입 없는 바이트(크기만)타입이 있는 객체(Job, 메시지, 송신 컨텍스트)
아는 것크기 등급생성자, Reset()
반납 때내용 무시(연결 정보를 덮어씀)상태를 비워야 함

둘이 만나는 곳은 포함이다. 예: 메시지 객체는 ObjectPool에서, 그 안의 가변 길이 본문 바이트는 BufferPool(PooledBuffer)에서 빌린다. sizeof(객체)는 본문 길이와 상관없이 늘 같다. 패킷을 객체로 둘지 바이트로 둘지는 Messaging의 "객체 큐 vs 직렬화 큐"에서 정한다(직렬화 큐면 BufferPool만 쓴다).

질문 2: 바이트 단위면 BufferPool로 ObjectPool도 되지 않나?

"소멸시키고 메모리만 재사용"(1A)이면 된다(Rent(sizeof(T)) + placement new). 하지만 세 가지가 걸렸다.

  • 가장 작은 등급이 256B라 40B 객체도 256B를 차지한다(약 6배 낭비).
  • new std::byte[]는 16바이트 정렬이라 alignas(64) 타입을 올릴 수 없다.
  • 매번 소멸·생성하면 객체 안 vector·string의 할당이 그대로 남는다. 풀을 쓰는 큰 이유가 사라진다.

그래서 1B: 살려 두고 Reset()을 골랐다. 살아 있는 객체는 덮어쓸 수 없어 BufferPool과는 따로 만든다.

질문 3: Reset은 메모리를 미는 한 줄이면 되지 않나?

한 줄 Reset결과
memset(this, 0, sizeof(*this))vector가 든 객체는 내부 포인터가 0이 되어 누수·크래시(정의되지 않은 동작). 단순 값만 있을 때만 안전
*this = T{}정확하지만 새 빈 vector를 대입해 용량이 사라진다(= 1A와 같아짐)
values.clear(); id = 0; ...정답. 용량은 남기고 내용만 지운다. 대신 필드를 하나씩 적어야 한다

위험은 "쓰기 어려움"이 아니라 나중에 멤버를 추가하며 Reset()에 넣는 것을 잊는 것이다. 그래서 concept Poolable로 noexcept Reset()이 없으면 컴파일되지 않게 했다.

측정: C++이 C#만큼 나오는가

객체 하나를 빌려 값을 쓰고 바로 반납(같은 스레드). 모든 스레드를 합친 초당 횟수(클수록 좋다). 두 언어 모두 전체 840만 회, 미리 만든 스레드 N개가 같이 출발하는 같은 틀(ThreadTeam). C++은 Google Benchmark 중앙값, C#은 BenchmarkDotNet(1 / Mean). Plain = 값 하나, WithList = vector/List에 하나 넣기.

읽는 법

  • C++ 풀은 C# 풀보다 빠르다(Plain 1스레드 약 8배, 8스레드 약 200배). C# DefaultObjectPool은 스레드 캐시가 없고 모든 스레드가 같은 배열을 Interlocked로 다퉈서(true sharing) 스레드가 늘수록 더 느려진다.
  • C++ 풀은 C# new보다도 빠르다(Plain 1스레드 1.8배, WithList 8스레드 약 4배). GC 할당은 포인터를 미는 것뿐이라 매우 싸서, C#은 작은 객체를 풀에 넣으면 오히려 손해다. C#은 만들기 비싼 객체만 풀에 넣고 작은 객체는 new하는 것이 맞다(docs/naming.md). C# new Plain 1스레드는 측정마다 1.4~2.1ns로 흔들렸다.
  • C++은 반대다. new/delete가 비싸서(내부 vector까지 할당하면 약 65배 차이) 풀이 크게 이긴다.

측정 틀을 두 번 고쳤다(Codex 리뷰)

  1. 1차 R1: 처음 C#은 Parallel.For(8만 회)였다. MaxDegreeOfParallelism은 상한일 뿐이라 N개 스레드가 실제로 동시에 도는지 보장하지 않는다. → 측정마다 전용 스레드 N개를 만들고, 횟수를 C++과 같은 840만 회로.
  2. 2차 R1: 측정마다 스레드를 만들면 생성 비용과 출발 시차가 섞인다. 실제로 Noop이 8코어 8스레드에서 3.4~3.8배만 늘어 CLAUDE.md 규칙("Noop이 스레드 수만큼 늘지 않으면 믿지 않는다")에 걸렸다. → 두 언어 모두 ThreadTeam(스레드를 미리 만들고 barrier로 같이 출발·같이 끝)으로.

그래도 Noop은 8스레드에서 약 5배까지만 늘었다(이 PC는 물리 8코어, 논리 16개). 확인한 것: 객체를 64바이트로 정렬해도 같다(false sharing 아님), 스레드를 물리 코어마다 고정하면 오히려 느려졌다(1스레드 845M → 338M). 그래서 "스레드를 늘리면 몇 배"라는 확장성 수치는 내세우지 않고, 같은 스레드 수·같은 틀에서의 언어 간 비교만 결론으로 쓴다. 이 비교는 틀의 한계보다 차이가 훨씬 크다(수 배~수백 배). 원인 조사는 후순위(PROGRESS).

덤으로 알게 된 것: BufferPool이 느린 이유

같은 구조인데 ObjectPool(헤더 템플릿, 모두 인라인)은 1스레드 625~845M/s, BufferPool(.cpp에 있어 호출이 인라인되지 않음)은 200~290M/s다. 후순위 목록의 "BufferPool 2판 최적화 ① 빠른 길을 헤더 inline으로"의 근거가 됐다(PROGRESS).
