008 · Memory: BufferPool 2판, 첫 벤치마크

C++ · C# · 2026-11-26 · 커밋 2209890 ~ 77613dd

무엇을 했나. 벤치마크를 처음 들여와(Google Benchmark, BenchmarkDotNet) 007의 BufferPool 1판을 쟀더니, 풀을 쓰지 않는 new/delete보다 느렸다. 스레드마다 캐시를 두는 2판으로 바꾸고, 빌리는 스레드와 반납하는 스레드가 다른 경우(Lane이 빌리고 IOCP 스레드가 송신 완료 후 반납)까지 재서 캐시 개수를 정했다.

그 과정에서 측정 도구의 문제(여러 스레드 결과가 눌림)와 빌드 버그(헤더만 바꾸면 다시 컴파일되지 않음)를 찾아 고쳤다. 고민 과정은 개발일지 docs/journal/bufferpool.html, docs/journal/benchmark.html에 있다.

1판은 왜 바꿨나

원인내용
스레드 1개에서도 느림빌리고 반납하는 한 번에 원자 연산 6번(mutex 잠금·해제 4번 + 빌려 간 수 카운터 2번) ≈ 30ns. Windows 기본 힙은 약 20ns. 풀이 아끼는 비용보다 더하는 비용이 컸다
스레드가 늘수록 느려짐모든 스레드가 같은 mutex·카운터를 써서 캐시 라인이 코어 사이를 오갔다(true sharing)

2판 구조

부분하는 일
전역 풀 BufferPool::Shared()프로세스에 하나, 프로그램 끝까지 산다(constinit). 등급마다 mutex + 묶음 목록(1판 구조). 스레드 캐시에 남은 버퍼가 끝날 때 늘 돌아올 곳이 있다
스레드 캐시스레드마다 등급별로 반납된 빈 버퍼를 들고 있다. 보통의 빌리기·반납은 여기서 끝난다(락·원자 연산 없음)
묶음 이동캐시가 넘치면 절반을 한 묶음으로 전역에 보내고, 비면 한 묶음을 가져온다. mutex는 묶음 하나에 한 번
스레드 종료캐시에 남은 버퍼를 전역으로 보낸다. 캐시가 이미 소멸한 뒤의 반납은 전역으로 바로(리뷰 R1)
캐시 개수등급마다 스레드 하나가 256KB까지(4~64개, 묶음은 절반): 256B·1KB·4KB 64개, 16KB 16개, 64KB 4개. 스레드당 최대 약 848KB
빌려 간 수Debug에서만 센다(모든 스레드가 같은 카운터를 쓰면 경합)
PooledBuffer쓰는 법 그대로. 풀이 하나라 풀 포인터가 빠져 16바이트

버퍼가 쓰이는 곳: 수신 버퍼는 세션이 고정으로 들고 있어 반납이 없다. 송신 버퍼는 패킷마다 빌리고, 보내기가 끝났을 때 IOCP 스레드가 반납한다(빌리는 스레드 ≠ 반납하는 스레드). 그래서 묶음 이동이 필요하다.

측정 결과

값은 모든 스레드를 합친 초당 (빌리기 + 반납) 횟수, 3회 중앙값. 측정 방법: 스레드 N개가 전체 840만 회를 나눠 하고 모두 끝날 때까지의 시간(C# 측정과 같은 방식). 측정 틀 기준(Noop)이 스레드 수만큼 느는 것을 확인한 뒤의 값이다.

측정 도구와 빌드에서 찾은 문제

문제원인고침
여러 스레드 결과가 모두 눌림(아무 일도 안 하는 반복도 8스레드에서 1.2배)benchmark::DoNotOptimize의 MSVC 구현이 값을 전역 변수 하나에 쓴다(역어셈블로 확인). 모든 스레드가 같은 캐시 라인에 씀스레드 안 반복에서는 스레드마다 자기 volatile 변수에 쓴다(4e8eaee). CLAUDE.md에 "여러 스레드 벤치마크 규칙"(Noop 기준 같이 재기)
헤더만 바꾸면 다시 컴파일되지 않음한국어 VS 컴파일러가 /showIncludes를 한국어로 출력해 ninja가 헤더 의존을 기록하지 못했다build.ps1에서 컴파일러 출력을 영어로 고정(VSLANG=1033, b4e0bbd)

원인을 좁힌 과정(측정 시간, 코어 제한, 우선순위를 차례로 의심 → C# Noop은 정상 → 표준 C++만으로도 정상 → Bench 코드 안)은 docs/journal/benchmark.html. "하드웨어는 같은데 C#은 되잖아"라는 질문이 방향을 바꿨다.
