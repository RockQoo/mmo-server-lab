005 · Base: StrongId, Ruid, RuidGenerator

C++ · C# · 2026-11-26 · 커밋 11f157a, a642818, 9060ccb, e7c7cb2

무엇을 했나. 모든 서버에서 유일한 64비트 ID Ruid와 발급기 RuidGenerator를 C++과 C#으로 만들었다. 플레이어, 길드, 우편, 아이템 등 모든 콘텐츠 ID의 원본이 된다. ID끼리 섞이지 않게 하는 타입 StrongId<Tag>(C++)도 같이 만들었다.

004에서 "다음은 키로 Lane을 고르는 묶음"이라고 적었는데, 그 묶음이 고를 키(PlayerId, GuildId 등)의 모양을 먼저 정해야 해서 이 단위를 앞에 넣었다. 특히 아래 비트가 순번인 ID는 id % N으로 나누면 한 Lane에 몰린다(아래 "Lane 고르기와의 관계").

비트 배치

칸정한 이유
부호 0SQL Server BIGINT는 부호가 있다. 63비트만 쓰면 C++ int64_t, C# long, DB에 캐스팅 없이 들어가고 음수가 나오지 않는다
Timestamp 41 (맨 위)나중에 만든 ID가 항상 크다. 클러스터드 인덱스에 늘 끝으로 붙어 페이지 분할이 적고, ID 범위로 기간 조회가 된다. 기준 시각을 2026년으로 잡아 1970년 기준보다 56년을 아낀다
Realm 7서버 통합 때 ID가 겹치지 않게 렐름 번호를 ID 안에 둔다. 번호는 모든 지역에서 하나의 번호표로 매긴다(지역마다 1부터 매기면 통합 때 겹친다). 0은 예약이라 실제 ID는 0이 될 수 없고, 0을 "없음"으로 쓴다
Node 6같은 렐름에서 ID를 만드는 프로세스 번호. 순번(CAS)은 프로세스 안의 스레드끼리만 나눠 쓰므로 프로세스끼리는 이 칸이 갈라 준다. 존을 쪼개며 늘어날 수 있는 쪽이라 렐름보다 여유를 줬다
Sequence 9MMO에서 한 프로세스가 같은 1ms에 만드는 ID는 레이드 보상 수백 개 수준이다. 512를 넘으면 다음 ms까지 기다릴 뿐 겹치지 않는다. 대량 발급은 나눠서 한다(어차피 DB 쓰기도 나눠서 한다)

비트 배분과 기준 시각은 첫 ID를 발급한 뒤로 바꾸지 않는다. DB에 남은 ID와 뜻이 어긋난다.

ID 타입: StrongId

ID는 정수지만 아무 정수나 들어가면 안 되고, PlayerId 자리에 GuildId가 들어가도 안 된다. 그래서 ID마다 다른 타입을 만든다. 실행 비용은 정수와 같다(크기 8바이트, 레지스터로 전달, 비교·해시는 인라인).

// C++: StrongId 템플릿. Ruid는 상속(자기 멤버가 필요), 콘텐츠 ID는 별칭
class Ruid : public StrongId<RuidTag> { ... };
using PlayerId = StrongId<struct PlayerTag>;   // 나중에 CodeGen이 만든다

// C#: ID마다 readonly record struct
public readonly record struct Ruid : IComparable<Ruid> { public long Value { get; } public int Realm => ...; }

모양이 두 번 바뀌었다.

  1. enum class Ruid : std::int64_t: 직렬화·비교·해시가 공짜. 하지만 Ruid도 성질은 StrongId와 같고, 콘텐츠 ID는 어차피 StrongId가 필요하다. 같은 성질의 타입을 두 방법으로 만들지 않도록 StrongId로 통일했다.
  2. using Ruid = StrongId<RuidTag>(별칭): 별칭은 같은 타입에 이름만 붙인 것이라 Ruid만의 멤버(Create, Realm())를 붙일 수 없었다. 칸 꺼내기가 자유 함수 RuidRealm(id), 발급이 RuidGenerator::Global().Next()로 C#과 사용법이 달랐다.
  3. class Ruid : public StrongId<RuidTag>(상속, 지금): StrongId 성질은 그대로 받고 Ruid::Init/Ruid::Create/id.Realm()/Ruid::MaxRealm을 붙였다. 가상 함수도 멤버 추가도 없어서 크기 8바이트·단순 복사(static_assert)다. 표준은 부모의 std::hash·std::formatter 특수화를 자식에 쓰지 않아서 Ruid용을 부모 것을 물려받는 한 줄씩 더 적었다.

클래스: RuidGenerator

C++
  • 마지막으로 낸 (시각 << 9 | 순번)을 원자 변수 하나에 둔다. 따로 두면 둘 사이에 다른 스레드가 끼어든다
  • CAS에 성공한 스레드만 그 값을 가져간다 → 같은 (시각, 순번)은 두 번 나오지 않는다. lock-free(경쟁하면 재시도)
  • 순서 보장이 필요한 다른 메모리가 없어 memory_order_relaxed. 한 원자 변수의 CAS는 모든 스레드가 같은 순서로 본다
  • 초깃값 -1 = "아직 안 냄"(산술 시프트로 시각 -1). 그래서 시각 0부터 낼 수 있다
  • 복사·이동 금지: 복사하면 두 발급기가 같은 ID를 낸다
C#
  • sealed class, 같은 알고리즘
  • Volatile.Read로 읽고 Interlocked.CompareExchange가 돌려준 값으로 재시도
  • 전역 진입점은 Interlocked.Exchange로 "한 번만"을 지키고 Volatile.Write로 내보낸다
  • 범위 검사는 is >= .. and <= .. 패턴

시계: 왜 단조 시계인가

시스템 시계는 시간 동기화나 VM 복원으로 뒤로 갈 수 있다. 그대로 쓰면 이미 낸 (시각, 순번)이 다시 나온다. 시계 역행은 못 막지만 ID가 겹치는 것은 막을 수 있고, 겹친 ID는 DB에 남아 되돌릴 수 없다.

그래서 시작할 때 실제 시각을 한 번만 읽고, 그 뒤로는 뒤로 가지 않는 시계로 흐른 시간만 더한다. 실행 중에는 역행이라는 상황 자체가 없어서 "역행 감지·대기·카운터" 코드가 필요 없다.

  • 남는 위험: 재시작 사이에 시스템 시계가 뒤로 가 있으면 꺼지기 전 ID와 겹칠 수 있다. DB 단계에서 "이 노드가 마지막으로 쓴 시각 이후부터" 시작 검사를 붙인다(주석에 주의사항으로 적음)
  • 대가: 몇 주씩 켜 두면 ID 안의 시각이 실제와 몇 초 벌어질 수 있다. ID 안의 시각은 "대략 언제"용이고 순서는 그대로다
  • 가짜 시계가 뒤로 가는 경우(테스트)에도 마지막 시각을 유지해 겹치지 않고 커진다

Lane 고르기와의 관계

Lane이 8개면 id % 8은 맨 아래 3비트, 즉 순번의 아래 3비트만 본다. 캐릭터·길드·우편처럼 드물게 만드는 ID는 순번이 늘 0이라 전부 Lane 0으로 간다. 시험으로 Lane 8개에 나눈 결과:

코딩 규칙 변경

고정 폭 정수는 std:: 없이 쓴다(int32_t). 크기가 정해져야 하는 자리(직렬화, 비트 배치, C#과 같은 값)에는 고정 폭 정수를 쓰고, 짧게 쓰려고 std::를 뺐다. MSVC·GCC·Clang 모두 전역 이름을 넣어 준다. std::size_t, std::byte는 그대로다(docs/coding-style.md "정수 타입"). 기존 C++ 코드도 한 번에 바꿨다.

나중에

  • 콘텐츠 ID 타입(PlayerId, GuildId …): 프로토콜/CodeGen 단계에서 C++ StrongId<Tag>, C# record struct로 생성
  • 재시작 사이 시계 역행: DB 단계에서 노드별 마지막 시각 기록 + 시작 검사
  • 노드 번호 배정: 지금은 실행 인자·Config, Coordinator 단계부터 빌려 주는 방식(중복 거절)
  • 순번 소진 때 다음 ms를 미리 빌려 쓰기, 노드별 대신 Lane별 발급기: 벤치마크로 필요한지 본다
  • 시각 위 vs 아래의 INSERT 처리량·래치 대기·페이지 채움률(DB 단계)
