012 · 직렬화 최적화: 인라인, 통째 복사(Blittable)

C++ · C# · 2026-11-28 · 커밋 194f20a ~ 8717d3d

무엇을 했나. 970바이트 인벤토리 패킷(칸 60개 × 필드 3개)을 쓰는 데 C++ 789ns, 읽는 데 958ns가 들었다(performance.html 사례 10, 계획 D). 원인을 하나씩 나눠 재며 두 단계로 고쳤다. ① 바이트 쓰기·읽기 함수를 헤더로 옮겨 인라인하고 쓰기는 vector::insert 대신 resize + memcpy, ② 메모리를 그대로 복사해도 같은 바이트인 타입(Blittable)은 배열을 memcpy 한 번으로. 쓰기는 789 → 12.9ns(61배), C#도 208 → 10.5ns가 됐다.

바이트 형식은 바뀌지 않는다. 통째 복사는 "필드마다 쓴 바이트와 같을 때만" 쓰는 빠른 길이라, 두 언어 정답 hex 파일 테스트가 그대로 통과한다. SERIALIZE_FIELDS 쓰는 법과 CodeGen이 만들 코드도 그대로다.

정한 것

항목결정이유
① 인라인C++ WriteBytes·ReadBytes를 .cpp에서 헤더로. 쓰기는 resize 뒤 memcpy필드마다 다른 번역 단위 함수를 불러 인라인이 안 됐다. 인라인만 하면 읽기는 줄었는데 쓰기는 그대로라 insert가 원인임을 따로 확인했다
C#에는 ① 없음바꾸지 않음C# 필드 하나 쓰기는 약 1.3ns로 이미 JIT가 인라인한다(측정)
② 통째 복사 판별(C++)concept Base::Blittable<T>. bool을 뺀 기본형, 또는 SERIALIZE_FIELDS 클래스 중 필드가 모두 blittable · 선언 순서 그대로(필드 주소가 커지는 순서, consteval 비교) · 필드 크기 합 = sizeof컴파일할 때 정해져 실행 비용이 없다. 하나라도 아니면 예전처럼 필드마다 써서 바이트는 늘 같다. 따로 매크로를 두지 않고 SERIALIZE_FIELDS 하나가 알아서 고른다(꼭 빠른 길이어야 하면 static_assert(Base::Blittable<T>))
② 통째 복사 판별(C#)Blittable<T, TCodec>.IsBlittable: 코덱이 IsPlainCopy => true로 밝혔을 때만, 타입마다 처음 한 번 메모리를 무늬(2, 3, 4 …, 주기 200·199)로 채워 코덱으로 쓴 것·읽은 것과 비교. static readonlyC# 코덱은 그냥 함수라 필드 순서를 컴파일할 때 알 수 없다. JIT가 결과를 상수로 접어 분기도 사라진다. 써 보는 범위는 리뷰 R1·R2로 좁혔다(아래)
빠른 길이 쓰이는 곳C++ 객체 자신, vector·array·T[N]. C# 배열·List(CollectionsMarshal)패킷 안 반복 칸이 비용의 대부분이다
읽기 안전바이트가 개수만큼 없으면 resize 전에 실패. bool은 통째 복사 안 함거짓 개수로 큰 메모리를 잡지 못하게. 2 같은 값을 bool에 그대로 넣으면 미정의 동작

  • Inventory 읽기 C++ 110 vs C# 27ns: C++은 새 vector(960B)를 반복마다 malloc·free한다. 객체를 다시 쓰면 22.7ns라 약 87ns가 할당 비용이다(ReadReuse 벤치를 추가해 확인). C#은 GC 힙 할당이 싸고 비용이 나중에 GC로 온다.
  • Chat 읽기 C++ 70 vs C# 20ns: 이번에 바꾸지 않았다. UTF-8 검사 차이(BCL SIMD)로 보이지만 확인 전이라 계획 H에 가설과 합격선(30ns 이하)만 적었다.
