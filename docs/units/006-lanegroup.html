006 · Messaging: LaneGroup

C++ · C# · 2026-11-26 · 커밋 c6bd883, 1a674d1, 41e99f5

무엇을 했나. Lane 여러 개를 묶고 키로 Lane 하나를 고르는 LaneGroup을 C++과 C#으로 만들었다. C++ Lane에는 스레드 이름을 붙였다.

같은 키는 항상 같은 Lane으로 가므로 같은 키의 일은 넣은 순서대로 하나씩 처리되고, 다른 키끼리는 다른 Lane에서 동시에 돈다. 004에서 만든 Lane 하나로는 코어 하나만 쓰고, 대상마다 스레드를 만들면 스레드가 너무 많아진다. 그 사이를 잇는 단위다.

고르는 방법 두 가지

방법쓰는 곳어떻게
LaneFor(key)많고 모양을 모르는 키(PlayerId, GuildId, Ruid 등)키를 섞은 뒤(splitmix64 마무리 단계) Lane 수로 나눈다
At(index) / group[index]적고 오래 사는 대상(존)만들 때 번호를 정해 Lane을 받아 두고 계속 쓴다. 존 16개를 Lane 8개에 넣으면 2개씩 고르게 들어간다

순서는 Lane이 지킨다(같은 키 → 같은 Lane → Lane은 넣은 순서대로 하나씩). LaneFor가 Lane을 돌려주는 모양(group.LaneFor(id).Post(job))을 고른 이유는 순서가 아니라 쓰기 편함이다: Lane의 Post·IsInLane을 그대로 쓰고, 존은 Lane을 들고 있어 매번 계산하지 않는다. 키 A와 키 B 사이의 순서는 보장하지 않는다.

왜 key % N이 아니라 섞어서 나누나

Ruid의 맨 아래 9비트는 순번이다. 캐릭터·길드·우편처럼 드문드문 만드는 ID는 그 ms의 첫 번째라 순번이 늘 0이고, 값이 512의 배수가 된다. % 8은 아래 3비트만 보므로 전부 Lane 0이다. 실제 Ruid 모양으로 Lane 8개에 나눈 결과:

  • 시각 비트로만 나누면((id >> 22) % N) 같은 ms에 몰아서 만든 ID가 전부 한 Lane으로 간다. 시각과 순번을 둘 다 반영하는 게 섞기다
  • 섞기는 splitmix64(Java SplittableRandom 등에서 쓰는 공식)의 마무리 단계다. 곱셈 두 번
  • std::hash는 컴파일러마다(GCC는 값 그대로), C# HashCode는 실행마다 달라서 쓰지 않는다. 직접 옮긴 공식이라 C++과 C#이 같은 키에 같은 번호를 고른다(IndexFor 테스트가 같은 값을 확인)

종료 순서 (리뷰에서 찾은 버그)

처음에는 기본 소멸자를 썼다. 기본 소멸자는 Lane을 하나씩 "멈추고 바로 해제"한다. 그러면 Lane 0이 해제된 뒤에도 Lane 1에서 아직 도는 일이 Lane 0에 Post할 수 있고, 해제된 mutex·스레드를 건드린다(Lane끼리 일을 주고받으면 실제로 생긴다).

고친 뒤: 소멸자가 모든 Lane을 먼저 멈추고 그다음 해제한다. 멈춘 Lane에 넣는 Post는 안전하게 false를 돌려주고 그 일은 버려진다.

  • 확인: AddressSanitizer(/fsanitize=address)로 고치기 전 코드는 heap-use-after-free, 고친 코드는 오류 없이 false. 일반 빌드에서는 해제된 메모리 접근이 늘 크래시로 드러나지 않아(정의되지 않은 동작) ASan으로 따로 확인했다
  • 회귀 테스트: Lane 1의 일이 "자기 Lane에 넣기가 거절될 때(= 멈춤 시작)"까지 기다린 뒤 Lane 0에 넣는다. 처음엔 100ms 대기로 만들었는데, 시간은 순서를 보장하지 않아(부하가 높으면 깨짐) 순서로 맞췄다(2차 리뷰)
