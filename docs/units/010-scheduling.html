010 · Scheduling: TimerHeap, Scheduler

C++ · C# · 2026-11-28 · 커밋 d5846e0 ~ 70def23

무엇을 했나. "몇 초 뒤", "몇 초마다" 일을 담당 Lane에서 돌려 주는 Scheduler를 두 언어로 만들었다. C++은 시각 순서 약속 목록 TimerHeap(우선순위 큐 + 해시)과 타이머 스레드 하나로, C#은 BCL TimeProvider.CreateTimer(런타임 타이머)로 만들었다. 두 언어 모두 일은 타이머 스레드가 아니라 등록할 때 넘긴 Lane에서 돈다. 그래서 그 Lane의 데이터를 락 없이 만진다.

함께 한 것: 흔히 더 빠르다고 하는 타이머 휠과 힙을 비교하는 벤치마크(힙 유지, performance.html 사례 15), 스레드 이름 붙이기 공용 함수 Base::SetCurrentThreadName, 코딩 규칙 "정수는 모두 고정 폭"과 lint 검사, C# CrashDump.Write 재시도 한 번.

흐름

C++ 락 순서는 Scheduler → Lane 하나뿐이다(Lane은 일을 자기 락 밖에서 돌리고, 회차는 Scheduler를 모른다). Lane에 남은 회차는 Entry를 shared_ptr로 따로 들고 있어 Scheduler보다 늦게 돌아도 안전하다.

C#에 없는 것과 이유

  • TimerHeap: 런타임 TimerQueue가 시각 순서 관리와 깨우기를 이미 한다. 같은 일을 하는 목록을 다시 만들 이유가 없다. 존 틱 안 타이머의 C# 자리는 ZoneServer 단위 때 정한다(후보 BCL PriorityQueue<TElement, TPriority>, 아직 정하지 않음).
  • 스레드 이름(SetCurrentThreadName): C# Lane과 Scheduler는 전용 스레드 없이 스레드 풀에서 돈다. 풀 스레드는 일마다 바뀌어 이름을 붙여도 뜻이 없다. 전용 스레드가 필요하면 BCL Thread.Name이 있다.
  • 주기 늦음 규칙을 C++처럼 맞추지 않았다: 차이는 주기보다 길게 늦었을 때만 보이고, 런타임 규칙도 몰아서 실행하지 않는다는 점은 같다. .NET 소스(TimeProvider.cs, Timer.cs의 FireNextTimers)로 확인한 내용은 사례 15에 있다.

벤치마크: TimerHeap vs TimerWheel

비교용 한 단계 타이머 휠(1ms × 4096칸)을 Bench에만 만들어 같은 모양으로 쟀다(release, 한 스레드). 자세한 표, 막대 차트, 30초 답변은 docs/journal/performance.html 사례 15.

  • 휠이 2~3배 빠르고 지우기에서 차이가 가장 크다. 100만 개면 둘 다 메모리에 묶여 차이가 줄어든다(섞어 쓰기 213~235 vs 142~201ns).
  • 10만 개 존의 50ms 틱 하나(약 700연산)는 힙 약 75µs, 휠 약 25~33µs. 둘 다 틱의 0.15% 이하라 결과가 늘 같은 힙을 둔다.
  • 리뷰 R2(주기 일 노드 재사용) 뒤 다시 잰 값은 PC 부하로 흔들려(한 번짜리만 쓰는 실행 측정도 전보다 느리게 나옴) 위 표를 바꾸지 않았다. PC가 쉴 때 다시 잰다.

함께 바꾼 것

코딩 규칙: 정수는 모두 고정 폭(C++)

  • 카운터·인덱스·테스트 값까지 int 대신 int32_t. int·unsigned·long·short는 쓰지 않는다. 고정 폭 정수는 std:: 없이(int32_t). auto i = 0;은 int라 auto i = int32_t{0};.
  • 예외는 바깥이 모양을 정한 함수뿐이다(int main(), signal·CRT 처리기). 바로 윗줄에 "바깥 API 모양" 주석.
  • server-cpp/lint.ps1이 검사한다(문자열·주석은 지우고 대소문자 구분: Windows LONG은 잡지 않음). 기존 코드(Bench, Base, Log, Memory·Messaging 테스트, Lane)를 모두 고쳤다(902f96a, 057896e). docs/coding-style.md.

C# CrashDump.Write 재시도 한 번(eed9add)

  • 살아 있는 프로세스를 덤프하는 동안 다른 스레드가 메모리를 바꾸면 createdump가 일부만 읽고 실패할 수 있다(ERROR_PARTIAL_COPY, 테스트에서 10번에 한 번쯤).
  • ServerErrorException이고 메시지에 ERROR_PARTIAL_COPY나 HRESULT: 0x80004005가 있을 때만 반쯤 쓴 파일을 지우고 100ms 뒤 한 번 더 쓴다. 두 번째 실패는 그대로 던진다. 메시지 형식은 라이브러리 소스(ValidateResponseMessage)로 확인했다.
  • 실패를 일부러 만들 수 없어 재시도 자체의 테스트는 없다. 대신 Base.Tests release 40회 반복 실패 0.

나중에

  • C++ Lane::Stop도 같은 모양(joinable 확인과 join 사이 잠금 없음)이다. 지금 쓰는 곳은 모두 한 곳에서만 멈춰 이번 범위 밖으로 두고, 다음에 같은 방식으로 손본다.
  • 닫힌 Lane을 가리키는 주기 일은 두 언어 모두 Cancel·Stop 전까지 회차를 계속 버린다(종료 순서상 Scheduler를 먼저 멈추는 규칙으로 막는다).
  • R2 뒤 TimerBench 다시 재기(PC가 쉴 때), 계층 휠은 필요해지면.
