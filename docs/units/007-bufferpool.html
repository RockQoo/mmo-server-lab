007 · Memory: BufferPool

C++ · C# · 2026-11-26 · 커밋 ae9706c, 5029024(VS 솔루션 구조)

무엇을 했나. 송수신·직렬화 버퍼를 다시 쓰는 BufferPool과, 빌린 버퍼를 자동으로 돌려주는 핸들 PooledBuffer를 C++로 만들었다. C#은 BCL ArrayPool<byte>.Shared를 그대로 쓰고 클래스를 만들지 않는다.

패킷마다 new/delete를 하면 할당 비용과 힙 잠금이 패킷 경로에 들어간다. 다음 단계인 Network(IOCP 송수신)와 "객체 큐 vs 직렬화 큐" 비교가 이 풀 위에서 돈다(풀 없이 비교하면 할당 비용 비교가 되어 버린다).

쓰는 모양

BufferPool pool;
auto buf = pool.Rent(1000);          // 1KB 등급 하나. buf.Data(), buf.Size() == 1024
ByteWriter w(buf.Data(), buf.Size());
sendOp->buffer = std::move(buf);     // 범위를 넘어가면 소유권을 옮긴다(IOCP 송신 등)
// 핸들이 소멸하거나 Reset() 하면 풀로 반납

정한 것

항목선택이유
크기등급 5개: 256B, 1KB, 4KB, 16KB, 64KB(4배씩). 요청 이상인 가장 작은 등급이동 패킷은 작고 스냅샷·인벤토리는 커서 등급 하나면 낭비가 크다. ArrayPool과 같은 방식
64KB 초과풀에 두지 않음. 그때 할당, 반납 즉시 해제드문 큰 패킷이 풀 메모리를 계속 차지하지 않게
스레드1판: 등급마다 mutex 하나이해하기 쉬운 판을 먼저 만들고, 스레드별 캐시 2판과 벤치마크로 비교해 근거를 남긴다
반납RAII 핸들 PooledBuffer(이동만, 복사 금지)아래
수명빌린 버퍼가 남은 채 풀이 사라지면 ASSERT해제된 풀에 반납하는 정의되지 않은 동작을 크래시로 바꾼다

왜 핸들로 한 번 더 감싸나 (C++만)

Rent/Return 날 포인터로도 동작한다. 핸들은 기능이 아니라 실수를 막는 장치다.

실수날 포인터PooledBuffer
반납 빠뜨림(중간 return)풀에서 버퍼가 계속 빠져나감소멸자가 반납
두 번 반납두 곳이 같은 버퍼를 빌려 데이터가 섞임복사 금지라 주인이 하나
크기를 틀리게 반납엉뚱한 등급에 들어감크기를 핸들이 기억
반납 뒤 사용다른 패킷 데이터를 덮어씀옮긴 뒤·Reset 뒤에는 빈 핸들

비용은 포인터 세 개(24바이트)이고 호출은 인라인된다.

C#에 만들지 않는 이유: 막는 힘이 소멸자와 "이동만"에서 나오는데 C#에는 둘 다 없다. struct로 감싸면 대입이 복사라 두 번 반납이 그대로 남고, class로 감싸면 빌릴 때마다 할당이 생겨 풀을 쓰는 의미가 줄어든다. 실수의 결과도 다르다(C++은 정의되지 않은 동작, C#은 GC 덕에 메모리는 안전). 그래서 C#은 관례대로 ArrayPool<byte>.Shared.Rent + try/finally Return. 네트워크는 나중에 System.IO.Pipelines가 버퍼 풀링을 맡는다.

반납 목록: vector에서 free list로 (lint에서 찾은 것)

처음에는 반납된 버퍼를 std::vector에 쌓았다. clang-tidy가 bugprone-exception-escape를 냈다. 반납은 소멸자에서 불려 noexcept인데 push_back은 할당하다 던질 수 있다(던지면 std::terminate).

고친 뒤: 반납된 버퍼 맨 앞에 다음 반납 버퍼의 주소를 적어 잇는다(침투형 free list). 가장 작은 버퍼도 256바이트라 포인터 하나를 담을 수 있다(static_assert로 크기·정렬 확인). 반납할 때 할당이 아예 없어 noexcept가 지켜지고 비용도 줄었다.
