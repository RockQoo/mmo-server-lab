009 · Memory: ObjectPool

C++ · C# · 2026-11-26 · 커밋 9080b49 ~ be963eb

무엇을 했나. 타입이 있는 객체를 다시 쓰는 풀 ObjectPool<T>와 핸들 PooledPtr<T>를 C++에 만들었다. 반납할 때 객체를 소멸시키지 않고 Reset()만 해서 내부 vector 용량까지 다시 쓴다. 구조는 BufferPool 2판(스레드 캐시 + 전역 묶음)과 같다. C#은 만들지 않고 MS 공식 NuGet Microsoft.Extensions.ObjectPool을 같은 조건으로 쟀다.

목표였던 "C++이 C#만큼 나오는가": C++ 풀은 C# DefaultObjectPool보다 스레드 1개에서 약 8배, 8개에서 약 200배 빠르고, C# new(GC 할당)보다도 빠르다. 고민 과정은 개발일지 docs/journal/objectpool.html.

정한 것

항목결정이유
BufferPool과의 관계형제(BufferPool = 날 바이트, ObjectPool = 타입 있는 객체). 객체 안의 가변 길이 바이트는 BufferPool에서 빌린다(포함)BufferPool로 객체를 담으면 256B 최소 등급 낭비, 16바이트 정렬 한계, 살아 있는 객체를 덮어쓸 수 없음
반납 때소멸하지 않고 Reset()(concept Poolable: 기본 생성 + noexcept Reset(), 없으면 컴파일 에러)내부 컨테이너 용량 재사용. memset은 정의되지 않은 동작, *this = T{}는 용량이 사라짐
구조스레드 캐시 64개 + 전역 묶음 32개(ObjectPoolTraits<T>로 타입마다 변경)BufferPool에서 측정으로 정한 값
풀 개수타입마다 전역 하나 ObjectPool<T>::Shared()thread_local은 타입마다 하나라 그대로 스레드 캐시가 된다
핸들PooledPtr<T> = std::unique_ptr<T, ObjectPool<T>::Deleter>(8B)표준이라 ->, std::move 그대로. 직접 만드는 코드가 거의 없다
블록[T][Links] 한 번에 할당, 연결 칸은 객체 뒤살아 있는 객체는 덮어쓸 수 없다(BufferPool은 빈 버퍼 안에 덮어씀)
BufferPool과 코드따로 작성(합치기는 후순위)측정이 끝난 BufferPool을 건드리지 않는다

  • C# DefaultObjectPool은 스레드 캐시가 없어(공유 배열 + Interlocked) 스레드가 늘수록 더 느려진다. GC 할당이 매우 싸서 작은 객체는 new가 낫다. 그래서 C#은 만들기 비싼 객체만 풀에 넣는다(docs/naming.md).
  • C++은 new/delete가 비싸서(내부 리스트까지 할당하면 약 65배 차이) 풀이 크게 이긴다.
  • 확장성 수치는 내세우지 않는다. 측정 틀 기준(Noop)이 물리 8코어 8스레드에서 약 5배까지만 늘었다(C++ 4.7배, C# 5.2배). 64B 정렬, 코어 고정을 실험했지만 원인이 아니었다. 같은 스레드 수·같은 틀의 언어 간 비교만 결론으로 쓴다(차이가 수 배~수백 배라 틀의 한계보다 훨씬 크다).
  • 덤: 같은 구조인데 헤더 템플릿(모두 인라인)인 ObjectPool이 1스레드에서 BufferPool(200~290M/s)의 3배쯤 빠르다. BufferPool 2판 최적화 "빠른 길 인라인"의 근거(PROGRESS 후순위).

측정 틀을 고친 것(리뷰)

문제고침
C# Parallel.For는 MaxDegreeOfParallelism이 상한일 뿐이라 N개 스레드가 실제로 도는지 보장하지 않는다. 횟수도 C++과 달랐다(8만 vs 840만)전용 스레드 + 같은 840만 회(d7059ce)
측정마다 스레드를 만들면 생성 비용·출발 시차가 섞인다(Noop 8스레드 3.4~3.8배)두 언어 모두 ThreadTeam: 스레드를 미리 만들고 barrier로 같이 출발·같이 끝(19fc324). CLAUDE.md 측정 규칙에 추가
ThreadTeam 생성 중 스레드 생성이 실패하면 오지 않을 작업자를 기다려 멈춘다만들지 못한 몫을 barrier에서 빼고, 만든 작업자를 멈춘 뒤 던진다(be963eb)

BufferPoolBench(C++)와 ArrayPoolBench(C#)는 기록된 수치를 유지하려고 아직 옛 틀이다. ThreadTeam으로 옮기는 일은 PROGRESS 후순위.

테스트

확인하는 것C++ gtest
Poolable이 아닌 타입(Reset 없음, Reset이 noexcept 아님, 기본 생성 불가)은 컴파일 안 됨, 핸들은 포인터 크기OnlyPoolableTypesCompile, HandleIsPointerSized
새 객체는 기본값, 반납하면 Reset되고 같은 스레드에서 같은 객체를 다시 줌, vector 용량은 남음RentGivesDefaultObject, ReturnResetsAndKeepsCapacity
이동해도 반납되지 않음MoveTransfersOwnership
캐시가 넘치면 묶음 하나를 전역으로, 스레드가 끝나면 캐시를 전역으로, 빈 캐시는 전역에서 묶음(Reset된 상태)OverflowSendsBatchToGlobal, ThreadExitFlushesCacheToGlobal, EmptyCacheTakesBatchFromGlobal
다른 스레드에서 반납하면 그 스레드의 캐시로ReturnOnOtherThreadGoesToThatThreadsCache
8스레드 동시, 빌리기 ≠ 반납 4쌍 × 2만 개: 같은 객체를 두 곳이 쥐지 않음ConcurrentRentNeverShares, CrossThreadRentReturnNeverShares
정렬이 큰 타입(alignas 64), 생성자 예외는 그대로 전달(반복 실행에서도 생성 경로, R2), 타입별 캐시 개수, Debug 빌려 간 수KeepsAlignment, ConstructorThrowPropagates, TraitsChangeCacheCount, DebugCountsRented(Debug만)

테스트마다 다른 타입(Item<번호>)을 써서 풀이 섞이지 않게 했다. --gtest_repeat=3 Debug·Release 통과.
